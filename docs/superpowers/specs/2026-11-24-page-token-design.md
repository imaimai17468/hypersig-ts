# ページ登録を暗号化トークンにする設計

## 目的

ページ登録（SSR で認可した Live View の集合）は今、作ったプロセスのメモリだけにある（`src/live-runtime.ts` の `pages`）。そのため次のことが起きる。

- 1 プロセスあたり 1,024 ページまでしか持てず、上限は変えられない。タブ 1 枚で 1 件使うので、利用者の多いサービスではすぐに古い登録が退避され、再取得が起きる。
- SSR したプロセスと SSE を受けるプロセスが違うと登録が見つからない。複数台構成ではスティッキールーティングか、Workers の Durable Object のように入口を一つにまとめる構成が要る。
- プロセスが再起動すると、開いているすべてのページが `reset` で再取得する。

Phoenix LiveView（`data-phx-session`）、Hotwire Turbo（`signed-stream-name`）、Livewire（スナップショットのチェックサム）と同じく、登録の中身をサーバーの鍵で保護したトークンにしてページに持たせる。どのプロセスでもトークンから登録を組み立て直せるようにする。ほかのフレームワークは署名だけで中身が読めるが、hypersig の props にはテナント ID のような値が入りうるので暗号化する。

## 合格の基準

- あるランタイムで SSR したページの SSE を、同じ鍵を持つ別のランタイム（別プロセスを模した別インスタンス）で受け、Topic の更新が届く。
- ランタイムを作り直しても（再起動を模す）、有効期限内のページは `reset` せずに更新が続く。
- ページ数の上限がなくなり、サーバーのメモリにページ登録が残らない（接続中の SSE が持つ状態だけになる）。
- トークンの改ざん、別のセッション、期限切れ、知らない View、鍵の不一致を、それぞれ今の `expired` / `denied` / `unknown-view` と同じ結果で扱う。
- ブラウザが別のプロセスに接続し直しても、新しい接続の更新を古い version として捨てない。
- Thesis の文字列（View のキーなど）を手書きに戻さない。

## 目的にしないこと

- 外部ストア（Redis など）にページ登録を置く方式。検討して不採用にした（下記）。
- Pub/Sub の複数台対応。`PubSub` はすでに差し替えられる。
- 同じトークンでの二重接続を、プロセスをまたいで止めること。
- トークンの失効リスト。失効はセッションの照合（`authenticate` と `sessionId`）で行う。

## やってはいけないこと

- props や View の名前を、ブラウザから読める形でトークンに入れること。
- トークンを受け取ったときに、認可（`authorize`）や認証を飛ばすこと。今と同じく接続のたびに通す。
- 定義の ID がプロセスごとに変わること。同じコードなら、どのプロセスでも同じキーになる。

## 検討した方式

| 方式                                         | 内容                                                                                                 | 判断                                                                                                     |
| -------------------------------------------- | ---------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------- |
| A. 上限と寿命を設定できるようにする           | メモリに持つのはそのまま。スティッキー前提                                                           | 不採用。複数台と再起動の問題が残る                                                                       |
| B. 外部ストアに置く（`PageStore`）            | 登録をシリアライズして Redis などに保存する。メモリ版を同梱                                          | 不採用。ストアへの往復と運用対象が増える。トークン方式で同じ目的を満たせる                               |
| C. 暗号化トークンに入れる                     | SSR で登録を AES-GCM で暗号化し、`data-hs-stream` の URL に入れる。どのプロセスでも復号して組み立てる | **採用**。インフラを足さずに、どのインスタンスでも SSE を受けられる。LiveView や Turbo と同じ型の方式 |

B と C に共通する前提（登録を「View の名前と JSON の props」にする、名前をプロセス間で同じ ID にする）は C でも必要になる。

## 設計

### 登録の形

トークンに入れるのは次の値で、これ以外のサーバー状態は持たない。

```ts
interface PageClaims {
  format: 1;
  sessionId: string;
  expiresAt: number; // ミリ秒の UNIX 時刻
  views: { name: string; key?: string; params: JsonValue }[]; // トップレベルだけ
  snapshots?: Record<string, { revision: string | number; digest: string }>;
}
```

- 子の View は今と同じく、接続時に親を描画して組み立て直すので、トークンに入れない。
- `snapshots` は今の `initialSnapshot`（子のいないトップレベル View で、SSR 時の版と HTML）を置き換える。HTML 本体の代わりに SHA-256 のダイジェストを入れ、版が同じときの「SSR のまま表示する」判定と、その後の「HTML が同じなら送らない」判定はダイジェストで比べる。近道を使う条件は「SSR のまま表示する近道」の節に書く。
- 暗号化は WebCrypto の AES-GCM（Bun、Node、Workers のどれにもある）。JSON を暗号化し、IV と合わせて base64url にする。
- トークンが長すぎる（目安 6 KB を超える）と、SSR で View 名を含む例外にする。URL の長さの上限に当たる前に、開発中に気づけるようにする。

### トークンを HTML に書くタイミング

`page.runtime()` は View の描画より前に `<script data-hs-stream>` を書くことがあるが、トークンの中身は描画がすべて終わるまで決まらない。そこで `renderPage` は、描画のあいだ推測できない仮の文字列（乱数、base64url の文字だけ）をトークンの代わりに渡し、直列化が終わった文書の中の仮の文字列を本物のトークンに置き換える。`renderPage` の呼び出し方と `page.runtime()` は今のまま変えない。仮の文字列が文書に一度も現れなかったときは、そのまま返す（`runtime()` を置かないページ）。

### SSR のまま表示する近道

今は最初の SSE 接続のときだけ、SSR 時の版と現在の版が同じなら読み直さずに SSR の HTML をそのまま使い、使ったあとは登録から消す。トークンには「使った」と書けないので、近道を使ってよいかはブラウザが接続 URL で示す。

- ブラウザは、SSR の HTML のまま一度も morph も消去もしていないトップレベル View のキーを、接続 URL に `pristine` として並べる（`view` と同じ形式の繰り返しのパラメーター）。サーバーは、`pristine` にあり、トークンの `snapshots` にもある View にだけ近道を使う。
- ブラウザがその View を書き換えたら（更新の morph、認可を失ったときの消去、`clearViews()`）、そのキーは以後 `pristine` に入れない。消去したときは、ブラウザは `pristine` を付け直した URL で EventSource を開き直す。EventSource の自動の再試行は最初の URL を使い続けるので、消去のあとに古い URL で再試行して近道が効き、空のまま残ることを防ぐためである。更新の morph のあとは版が SSR と違うので、古い URL のままでも近道は効かない。
- `pristine` は利用者の表示の状態を伝えるだけで、認可には使わない。偽の値を付けても、影響はその利用者の画面が古いまま残ることだけである。
- パラメーター名は `src/protocol.ts` で一度だけ定義し、サーバーとランタイムが共有する。

### 鍵

- `createHypersig({ pageKeys })` と `createLiveRuntime({ pageKeys })` に鍵を渡す。配列の先頭で暗号化し、すべての鍵で復号を試す。鍵を入れ替えるときは、新しい鍵を先頭に足し、古い鍵を期限ぶん残してから外す。
- 鍵の形式（生の 32 バイト、base64 の文字列、`CryptoKey` のどれを受け付けるか）は実装で決める。どれでも型で示す。
- `pageKeys` を省くと、プロセスの起動時に乱数で鍵を作る。1 プロセスの構成は今までどおり設定なしで動き、再起動時は今と同じく `reset` で再取得する。省いたまま複数台で動かすと、別のプロセスに届いた接続は `reset` を繰り返すので、そのとき `onDiagnostic` に鍵の不一致（復号できなかったこと）を知らせる。

### 有効期限

- 今の「30 分使われなければ退避」は、トークンの `expiresAt` に置き換える。トークンは書き換えられないので、接続中の延長はしない。
- 期限は SSR から数える。既定は 12 時間で、`pageLifetimeMs` で変えられる。接続中の SSE は期限を過ぎても続く（認証と認可は今と同じく約 15 秒ごとに確認する）。期限は、切れたあとに接続し直すときだけ効き、`reset` で再取得する。
- 期限が長くても、ログアウトしたセッションのトークンはセッションの照合で `denied` になる。

### View の ID とトークンからの組み立て

- `name` を必須にし、一つのランタイムの中で一意にする。キーは今の `name-番号` ではなく `name` そのものになる。同じ親の下に複数置くときの `.key` は今と同じ。
- 定義は `hypersig.live()` / `hypersig.liveShared()`（core では `runtime.live()` / `runtime.liveShared()`）を呼んだ時点でランタイムに登録する。名前が重なると、Action と同じくその場で例外にする。何も描画していない新しいプロセスでも、名前から定義を引ける。
- ランタイムに登録していない定義を `page.view()` / `context.view()` に渡すと例外にする。
- 単体の `live()`（`src/live.ts`）は公開 API から外す。サンプル（Counter、TodoMVC、星評価）は `hypersig.live()` に書き換える。
- トークンにある名前がランタイムにない（デプロイで View を消した）ときは `unknown-view` ではなく `expired` と同じに扱い、`reset` で再取得する。

### props の型

- トップレベルの `page.view(definition, params)` の `params` を JSON にできる値（`JsonValue`：文字列、有限の数、真偽値、`null`、それらの配列、プレーンなオブジェクト）に型で制限する。`undefined`、`Date`、`bigint`、関数は型エラーになる。省略可能なプロパティを省くのは許す。
- 子の `context.view()` の `params` には制限をかけない（トークンに入らない）。
- 型で防げない値（`NaN`、クラスのインスタンスを `JsonValue` と見なした値など）は、SSR で JSON に直したものと元の値が食い違う。実装では、トークンに入れる前に一度 JSON にして読み戻した props で `subscribe` / `authorize` を通すかどうかを決める（下の「実装に任せること」）。

### 一つのページに一つの接続

- 同じプロセスの中では、今と同じくトークンごとに直前の接続を閉じる。そのための対応表は接続中のあいだだけ持ち、接続が終わると消す。
- プロセスをまたいだ二重接続は止めない。どちらの接続も同じセッションで認可を通るので、見えるものは変わらない。

### version

- ブラウザは要素ごとに、受け取った最大の version を覚えて古い更新を捨てる（`src/browser.ts` の `versions`）。別のプロセスに接続し直すと version は 1 から数え直すので、今のままでは更新を捨ててしまう。
- ブラウザは EventSource の `open`（自動の再試行で開き直したときも発火する）のたびに `versions` を空にする。同じ HTTP 応答の中では順序が保たれ、閉じた応答のフレームはあとから届かないので、version の比較は一つの応答の中だけで足りる。
- サーバーは接続ごとに version を 1 から数える。ページ登録で version を引き継ぐ処理は消える。

### アダプターと core の変更

- `renderPage` はトークンを作って返す（今の `crypto.randomUUID()` の代わり）。`openPage(token, keys, user)` は復号が要るので非同期になる。
- `OpenPage` の状態の名前は今のまま（`expired` / `denied` / `invalid-count` / `unknown-view` / `open`）。`unknown-view` は、ブラウザが示したキーがトークンの View にないときに使う。
- Hono アダプターの `/stream/:token` はそのまま。トークンは base64url なので URL のパスに入る。

### ドキュメントとサンプル

- `docs/architecture.md` の「状態とライフサイクル」「Workers の共有状態」「ページ登録はそれを作ったランタイムが所有する」の段落を、トークン方式に書き換える。
- Workers のサンプルは、Durable Object の再起動後に登録をリセットする説明を、トークンから続ける動作に直す。共有状態を Durable Object に置く構成はそのまま。
- サイトの英語と日本語のドキュメントで、ページ登録の上限、寿命、複数台構成の説明を直す。

## テスト

- 2 つのランタイムに同じ鍵を渡し、片方で SSR、もう片方で `openPage` して Topic の更新が届く。
- ランタイムを作り直しても、期限内のトークンで更新が届く。
- 改ざんしたトークン、別の鍵、期限切れ（時刻を引数で渡して確かめる）、別の `sessionId`、知らない View 名、ブラウザが示したキーがトークンにない場合。
- 鍵の入れ替え：古い鍵で作ったトークンを、新しい鍵を先頭にしたランタイムが受け付ける。
- 名前の重複と、未登録の定義を描画したときの例外。
- `snapshots` のダイジェストで、版が同じときに SSR のまま表示し、HTML を送らない。
- `pristine` にない View は、版が同じでも HTML を送る。認可を失って消去した View が、認可が戻った再接続で描画し直される（ブラウザテスト）。
- 仮の文字列の置き換え：`runtime()` を View より前に置いたページで、`data-hs-stream` に本物のトークンが入る。
- 型のテスト：`page.view` に `Date` や `undefined` を含む props を渡すと型エラーになる。子の `context.view` には渡せる。
- ブラウザテスト：SSE を別のサーバープロセスにつなぎ変えたあと（あるいは同じプロセスでランタイムを作り直したあと）も更新が DOM に反映される。

## 実装に任せること

- 鍵の形式、トークンの中の JSON の詳しいキー名、base64url の実装。
- `JsonValue` の型の細部（`readonly` の配列やオブジェクトを受け付けるか）。
- props を JSON で読み戻してから使うかどうか。
- トークンの長さの上限値。
- Workers のサンプルで鍵を渡す方法（シークレットのバインディングなど）。
- 改ざんしたトークンと鍵の不一致は、どちらも `expired`（`reset`）として扱う。診断では区別しない。
- トップレベルの `page.view` と子の `context.view` で `params` の型を分ける方法。

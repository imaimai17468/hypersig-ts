# カスタム要素で JS ライブラリをつなぐ設計

## 目的

hypersig.ts の Signal と式では書けない処理（地図、リッチテキストエディタ、グラフ、日付ピッカー、独自の入力部品など）を、ブラウザの JS で動かしたい場面がある。今は自分のスクリプトを読み込めば動かせるが、次の問題がある。

- ページとのつなぎ方に型がない。要素を探すセレクタも値の受け渡しも手書きになる。
- Live View の中に置くと壊れる。morph がライブラリの描いた中身をサーバーの HTML に戻し、DOMPurify は既定でカスタム要素を取り除く。

JS の部品をカスタム要素で包み、その属性とイベントを型付きで一度だけ宣言して Signal とつなぐ。Rust 版 hypersig の `Page::script` / `bind_attr` / `on_custom` / `El::foreign` に当たる機能を、宣言を 1 か所にまとめる形で作る。

## 合格の基準

- 星の評価のカスタム要素（数十行の JS）を使う例を足し、次が動く。
  - 星を押すと、要素のイベントで Signal が変わる。Signal を変えると、要素の属性が変わって星の表示が変わる。
  - 評価を Action で保存し、別のタブの Live View の更新で平均が変わっても、要素は消えず、要素が自分で描いた中身は元に戻らない。
- タグ名、属性名、イベント名、イベントの `detail` の型を、アプリのコードで 1 か所にだけ書く（`AGENTS.md` の Thesis）。
- 宣言にない属性やイベント名、型の合わない値は型エラーになる。

## 目的にしないこと

- 特定のライブラリ（Leaflet など）の包み方を用意すること。包むカスタム要素はアプリが書く。
- イベントの `detail` を実行時に検査すること。宣言は JS の側を記述するもので、照合はできない（下の「検査できないこと」）。
- プロパティ（`element.value = ...`）への束縛。属性だけを扱う。

## やってはいけないこと

- 受信した断片の中で、カスタム要素に `on*` や `style` の属性が通ること。
- カスタム要素の属性への束縛が、普通の要素の許可リスト（`bindAttr`）を緩めること。
- タグ名やイベント名をアプリが手で繰り返して書く必要があること。

## 検討した方式

| 方式                                                                        | 判断                                                               |
| --------------------------------------------------------------------------- | ------------------------------------------------------------------ |
| A. カスタム要素を型付きで一度だけ宣言し、宣言から描画・束縛・イベントを作る | **採用**。名前と型が 1 か所にまとまり、Thesis に合う               |
| B. Rust 版と同じく、汎用の属性束縛とカスタムイベントの宣言だけを足す        | 不採用。タグ名と属性名が手書きになり、要素ごとの型の結び付きが弱い |

## 設計

### 宣言

```ts
const rating = customElement<{
  attributes: { value: number; max: number };
  events: { rate: number };
}>("star-rating", { ownsChildren: true });
```

- `customElement<Spec>(tag, options?)` は、`src/element.ts` に置き、`hypersig.ts` から export する。
- `tag` は、カスタム要素の名前の規則（小文字の英字で始まり、`-` を含み、小文字の英数字・`-`・`.`・`_` だけ）を、リテラルの型で検査する。
- 属性の値の型は `string | number | boolean`。イベントの `detail` の型は `JsonValue`。
- イベント名は、小文字の英字で始まり、小文字の英数字・`-`・`.`・`:`・`_` だけのものに限る（型で検査する）。
- `ownsChildren: true` は、要素の中身を JS の側が描くことを表す（Rust 版の `El::foreign`）。

### 描画

```tsx
<rating.Element
  {...e.bindElement(rating, { value: e.score, max: 5 })}
  {...rating.on("rate", (detail) => [
    e.score.set(detail),
    save.call({ score: detail }),
  ])}
/>
```

- `rating.Element` は Hono JSX のコンポーネントで、宣言したタグ名の要素を描く。`ownsChildren` なら `data-hs-owns-children` を付ける。
- `Element` の props には、普通の HTML 属性（`id`、`class`、`aria-*`、`data-*` など、Hono JSX が要素に許すもの）と、宣言した属性を宣言の型で直接書ける（設計者の判断）。宣言した属性を直接書く場合は固定の値になり、Signal と結ぶ場合は `bindElement` を使う。同じ属性を両方で書いたときは、JSX の展開と同じくあとに書いたほうが勝つ。両方で書かないよう API ドキュメントに書く。
- `scope.bindElement(element, values)` は、Signal のスコープのメソッドとして足す。値には値か `Expr` を書け、キーと型は宣言の `attributes` で検査する。サーバーはスコープの値で評価して属性に書く（数値と文字列はそのまま文字列に、真偽値は真なら属性を付け、偽なら付けない）。束縛は `data-hs-attr` に入れる。
- `element.on(event, (detail) => stmts)` は、`data-hs-on-custom` に `[イベント名, 文の配列]` の組の配列を入れる。同じ要素に複数のイベントを付けられる。`detail` は宣言の型の `Expr` で、ワイヤ形式は新しい `["detail"]` ノードとする。

### ブラウザのランタイム

- **属性の束縛:** `data-hs-attr` の各キーについて、今の許可リストに加え、要素がカスタム要素（`localName` に `-` を含む）の場合だけ、`on` で始まらず、`style` ではなく、`data-hs-` で始まらない、小文字の名前を許す。普通の要素の許可リストは変えない。
- **イベント:** カスタムイベントは泡立たないことがあるので、文書全体での委譲ではなく、`data-hs-on-custom` を持つ要素に直接リスナーを付ける。描画のたびに新しい要素を探して付け、同じ要素に二重には付けない。イベントが起きたら、`event.detail` が `JsonValue` ならそれを、そうでなければ `null` を `["detail"]` の値として文を実行する。
- **中身を JS が描く要素:** 中身だけを残し、属性はサーバーの HTML に合わせる（設計者の判断）。Idiomorph の `beforeNodeMorphed` で、既存の要素が `data-hs-owns-children` を持ち、新しい要素と同じタグ名で、`id` が一致する（両方とも `id` がない場合も一致とみなす）とき、新しい要素の属性を既存の要素に写し（新しい側にない属性は消す。ただし `data-hs-pending` は今の規則どおり残す）、`false` を返して中身の morph を止める。`id` が一致しないときは、既存の要素を新しい要素で置き換える（中身は作り直しになる）。これにより、サーバーのデータから作った属性（`data-hs-on-custom` の中の Action の入力など）は常に最新になり、束縛は morph のあとの再描画でかけ直される。
- **一覧で使うとき:** 同じ種類の要素を兄弟に複数置く場合は、要素ごとに `id` を付ける。`id` がないと、行の追加や並べ替えで Idiomorph が別の行の要素を対応させ、その要素の中身（JS の状態）が別の行に残る。API ドキュメントに書き、例のテストでは並べ替えを扱わない。
- **DOMPurify:** `CUSTOM_ELEMENT_HANDLING` を指定し、タグ名はカスタム要素の名前の規則に一致するものを、属性名は `on` で始まらず `style` でない小文字の名前を許す。`allowCustomizedBuiltInElements` は `false` のまま。`FORBID_ATTR` の `style` と `data-hs-stream` はそのまま効くことを、テストで確かめる。

### スクリプトの読み込み

要素を定義するスクリプトは、アプリが `<script type="module" src={links["rating.js"].$path()}>` で読み込む。新しい API は作らない。CSP の `script-src 'self'` のまま動く。

### 検査できないこと

宣言は JS の側を記述するだけで、hypersig.ts はそれを JS と照合できない。JS が出さないイベントは何も実行せず、`detail` に宣言と違う値が来ても、そのまま式に渡る（`JsonValue` でなければ `null`）。API ドキュメントにこのことを書く。

### 例

`examples/rating/` を足す。

- `rating.js`: `ownsChildren` の対象として、light DOM に星のボタンを描くカスタム要素。押すと `rate` イベント（`detail` は数値）を出し、`value` 属性が変わったら表示を変える。
- `server.tsx`: 評価の平均を表示する Live View の中に、星の要素を置く。押した評価を Signal に入れ、Action で保存する。`bun run example:rating` で起動する。
- ブラウザテスト: 星を押すと Signal と属性が変わること、「クリア」ボタンで Signal を変えると星が変わること、別のタブで保存して Live View が更新されても、要素とその中身が残ること。

## 決まっていること

- 方式 A。宣言は `customElement<Spec>(tag, { ownsChildren })`。
- 束縛は Signal のスコープの `bindElement`、イベントは `element.on`。
- カスタム要素にだけ属性名の許可を広げ、普通の要素は変えない。
- 中身を JS が描く要素は、中身だけを残し、属性はサーバーの HTML に合わせる。一覧では要素ごとに `id` を付ける。
- `Element` には普通の HTML 属性と、宣言した属性を固定の値で書ける。
- スクリプトの読み込みはアプリが行う。

## 実装する人に任せること

- `Element` コンポーネントの props の型の書き方。
- 描画のたびにリスナーを付ける仕組みの具体的な形。

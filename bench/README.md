# Phase 4 の計測

同じカウンターと 500 行の固定一覧を使い、更新境界の位置だけを変えた。**一覧を含む境界**（`coarse`）は値と一覧を一つの Live View に置く。**値だけの境界**（`fine`）は、一覧をページの SSR で描画し、カウンター値を Live View に置く。両方のページに、別 Topic を購読する独立した Live View も置いた。

## 再実行

```sh
mise exec -- node node_modules/@playwright/test/cli.js install chromium
mise exec -- bun run bench:phase4 > phase4.jsonl
```

既定では 500 行、SSE 1 / 25 / 100 / 200 接続を試す。`BENCH_ROWS`、`BENCH_CONNECTIONS`（カンマ区切り）、`BENCH_ROUNDS` で変更できる。条件ごとに Bun サーバーを作り直す。1 接続は Chromium のブラウザで、残りは Node の Fetch で SSE を読み取る。実ブラウザのクリックから始まる操作を逐次実行し、全クライアントが同じカウンター値を受信したことを確認する。最初の 5 操作でウォームアップし、その後 25 操作を測る。

## 結果から選んだ変更

固定一覧を更新境界の外に配置した。200 接続では、SSE 1 件が **23,924 B から 102 B**、クリックから DOM 反映までの p95 が **76.8 ms から 17.1 ms**、更新後のサーバー RSS が **534.5 MiB から 124.3 MiB** に下がった。200 接続 × 25 操作で配信した SSE の合計は **119,618,800 B から 508,800 B** になった。初期 SSR にはどちらも 500 行を含む。

1 操作あたりの対象 View の描画回数は両方式とも接続数と同じだった。独立した View の再描画は全 8 条件で **0 回**。独立した View の認可は再確認され、200 接続の 25 操作では **5,000 回**だった。性能改善は更新境界の配置で得られたため、HTML Fragment の形式、DOM morphing、認可の再確認間隔は既存のままとした。

## 接続間での描画共有

同じ値を見る複数の認可済み接続に限定し、JSX と HTML の直列化を共有した。Apple M2 Pro のループバックで25接続と200接続、各12操作を比較した。

```sh
BENCH_CONNECTIONS=25,200 BENCH_ROUNDS=12 mise exec -- bun run bench:phase4
BENCH_CONNECTIONS=25,200 BENCH_ROUNDS=12 BENCH_SHARE_RENDER=1 mise exec -- bun run bench:phase4
```

| 200 接続       | 12 操作の JSX 描画回数 | 全接続への配信完了 p95 | SSE 1 件 |
| -------------- | ---------------------: | ---------------------: | -------: |
| 一覧を含む境界 |             2,400 → 12 |        108.2 → 59.9 ms | 23,924 B |
| 値だけの境界   |             2,400 → 12 |         52.0 → 51.0 ms |    102 B |

JSX の描画回数が減っても、全接続に断片を送信するので配信量は同じ。値だけの境界では全配信完了時間の差も小さかった。共有と更新境界の調整はそれぞれサーバー描画と配信量に効く。別フレームワークとの性能比較や上限接続数の計測は含まない。[生データ](results/phase4-shared-m2-pro.jsonl)

## 接続間での読み取り共有

200接続から同じカウンターを購読し、12操作を逐次実行した。バージョンごとの値を SQLite に記録し、各 SELECT の前に12msの待ちを入れた。両条件で JSX 描画を共有し、読み取り共有の有無だけを切り替えた。版の選択は、コミット時に更新したメモリ上の値を使った。

```sh
BENCH_CONNECTIONS=200 BENCH_ROUNDS=12 BENCH_READ_DELAY_MS=12 BENCH_SHARE_RENDER=1 mise exec -- bun run bench:phase4
BENCH_CONNECTIONS=200 BENCH_ROUNDS=12 BENCH_READ_DELAY_MS=12 BENCH_SHARE_LOAD=1 mise exec -- bun run bench:phase4
```

| 更新境界       | 12操作の SQLite SELECT | 全接続への配信完了 p95 |
| -------------- | ---------------------: | ---------------------: |
| 一覧を含む境界 |             2,400 → 12 |         69.6 → 68.2 ms |
| 値だけの境界   |             2,400 → 12 |         58.9 → 59.0 ms |

この条件では、1操作あたりの SELECT が200回から1回に減った。全接続への配信時間は同程度だった。ローカルの SQLite と固定の待ち時間を使った比較で、外部 DB の接続プールやクエリ待ち行列は計測範囲外とした。[生データ](results/phase4-load-sharing-m2-pro.jsonl)

## 複数のプロセスへの配信（Redis Pub/Sub）

カウンターのサンプルを `REDIS_URL` つきで 1〜3 プロセス立て、`createRedisPubSub()` と `Bun.RedisClient` で変更を配った。比較のため、同じ接続数を 1 プロセスのメモリ版（`REDIS_URL` なし）でも測った。SSE の接続は Node の Fetch で開き、各プロセスに順番に振り分けた。接続ごとに別のセッションを使う（1 セッションの SSE は `maxStreamsPerSession` で 16 本まで）。最初のプロセスに `increment` の Action を送ってから、全プロセスの全接続がその値の `html-update` を受け取るまでを 1 回とし、逐次実行した。最初の 5 回でウォームアップし、その後 25 回を測る。

```sh
BENCH_CONNECTIONS=100,300,1000,3000 mise exec -- bun run bench:multi > multi-instance.jsonl
```

`redis-server`（`REDIS_SERVER` で変更できる）を空いたポートで起動し、終了時に止める。既定は 100 / 300 / 1000 接続で、`BENCH_CONNECTIONS`、`BENCH_ROUNDS`、`BENCH_SETUPS`（`memory:1,redis:1,redis:2,redis:3` の形）で変更できる。`memory` はメモリ版の Pub/Sub と値、`redis` は Redis の Pub/Sub と Redis に置いた値、`redis-pubsub` は Redis の Pub/Sub とプロセスのメモリに置いた値（1 プロセスだけ。カウンターの `COUNTER_COUNTS_IN_MEMORY=1`）を使う。条件ごとにカウンターのプロセスを立て直し、Redis を空にする。

### 実測値

- 1 プロセス同士では、Redis 版の配信完了はメモリ版より 13〜15% 遅い（1000 接続で 75.6 → 85.8 ms）。Redis 版では、購読の通知が Redis を往復するのに加えて、カウンターの `load` が接続ごとに Redis の `GET` で値を読む。この表だけでは 2 つを分けられないので、下の[通知と読み取りを分けた計測](#通知と読み取りを分けた計測)で分けた。差のほとんどは接続ごとの `GET` だった。
- プロセスを増やすと、各プロセスが描画して送る接続が減るので、配信完了が短くなる。1000 接続では 3 プロセスで **75.6 ms から 39.9 ms**（1.9 倍）、3000 接続では **229 ms から 123 ms**（1.9 倍）になった。その代わり、プロセスの合計 CPU は 1000 接続で約 72%、3000 接続で約 68% 増えた。これは 12 コアの 1 台の中で処理を並列にした効果で、複数のマシンに広げたときの伸びを示すものではない。最初のプロセス（発行した側）とほかのプロセスの配信完了 p50 の差は 1 ms 未満で、どちらが先とも決まらなかった（プロセスごとの値は JSONL の `processDeliveryMs`）。発行した側も Redis から通知を受けてから描画するため。
- プロセスの合計 CPU は、プロセスを増やすほど増えた（1000 接続で 128 → 221 ms）。どのプロセスも接続ごとに認可・読み取り・描画をし、Redis 版では読み取りが `GET` になる。Redis の CPU は 1 更新あたり数 ms で、ほとんどが接続ごとの `GET`。`PUBLISH` は 1 更新 1 回で、受け取るのは Topic を購読するプロセスだけ。
- メモリ版で Action の応答が遅いのは、`publish` が同じプロセスの購読者に通知を積み、その描画と応答が同じイベントループを取り合うため。Redis 版の `publish` は Redis が受け付けた時点で終わり、描画は通知が届いてから始まる。

範囲と限界：

- すべてを 1 台で動かしたので、プロセスどうしと計測スクリプトが CPU を取り合う。計測スクリプト（1 つの Node プロセス）も全接続のストリームを読み、1 更新あたり 1000 接続で約 20 ms、3000 接続で約 67 ms の CPU を使う（JSONL の `driverCpuMsPerUpdate`）。3 プロセスの条件では、1 更新にかかる時間のおよそ半分、計測スクリプトが CPU を使っている（1000 接続で 41.8 ms 中 20.9 ms、3000 接続で 127 ms 中 65 ms）ので、計測スクリプトの読み取りも配信完了の時間に入っている。別々のマシンやネットワーク越しの遅延は含まない。
- 3000 接続より上は測っていない。計測スクリプトは接続ごとにログイン、ページの取得、SSE で最大 3 本の TCP 接続を使い、macOS の一時ポート（49152〜65535）が上限になる。条件の間では、サーバー側から接続を閉じ、計測スクリプト側に TIME_WAIT が残らないようにした。
- 更新は 1 回ずつ逐次で、同時に多くの Action を送ったときの性能や、持続できる最大の更新頻度は測っていない。読み取りの共有（`liveShared`）を使っていないので、接続ごとの `GET` はそのまま残る。
- Redis が届けるのは一度きりで、切断中の通知は失われる。この計測では切断を起こしていない。

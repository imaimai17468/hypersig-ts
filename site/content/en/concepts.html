Core concepts

The server owns the application state. The browser displays the rendered output and keeps local interaction state such as focus and unfinished input.

Changes on the server

  1. An Action validates the input and checks access.
  2. The application commits the change and publishes a typed Topic.
  3. Subscribed Live Views render their HTML on the server.
  4. SSE carries the resulting fragments to the browser, which updates their DOM boundaries.

A background job can publish the same Topic after committing a change.

Choosing View boundaries

Subscribe each Live View to the Topics that affect its output. The runtime keys each definition apart, and key is needed only when one parent places the same definition more than once. Use separate boundaries for independently changing regions. Put an order summary and its total in the same View if both should display the same revision.

The first page response already contains HTML. Live View components run on the server.

Adding browser interactions

You can add JavaScript to a server-rendered page. For example, it can show a preview while dragging or count characters as someone types. Send values to the server when saving, and publish the change to update other views from the committed result.

Connection recovery

The server associates displayed View keys with the authenticated page. A reconnect reads the current state again. Access is checked when the View is rendered and again before updates are sent.

Core concepts

The server owns the application state. The browser displays the rendered output and keeps local interaction state such as focus and unfinished input.

Changes on the server

  1. An Action validates the input and checks access.
  2. The application commits the change and publishes a typed Topic.
  3. Subscribed Live Views render their HTML on the server.
  4. SSE carries the resulting fragments to the browser, which updates their DOM boundaries.

A background job can publish the same Topic after committing a change.

Choosing View boundaries

Subscribe each Live View to the Topics that affect its output. The runtime keys each definition apart, and key is needed only when one parent places the same definition more than once. Use separate boundaries for independently changing regions. Put an order summary and its total in the same View if both should display the same revision.

The first page response already contains HTML. Live View components run on the server.

Adding browser interactions

You can add JavaScript to a server-rendered page. For example, it can show a preview while dragging or count characters as someone types. Send values to the server when saving, and publish the change to update other views from the committed result.

A JavaScript library, or a React component, goes in a custom element that you declare once as a value and implement with defineElement or reactElement. The declaration types the implementation: its props are the declared attributes, and its emit takes only the declared events. Such an island is not rendered on the server: the server renders the element and the children you give it, such as a fallback, and the element's JavaScript renders the rest in the browser. It does not use Shadow DOM. The server passes it attributes, including JSON, and the element sends events back as typed values. Set ownsChildren when the element's JavaScript renders its children. Such an element needs an id (a type error otherwise), and a Live View update keeps it and its children only when the tag and the id match. Custom elements

Widgets such as a combobox, tabs, or a disclosure panel are written with signal statements alone: on.keydown for keys, on.focusEnter and on.focusLeave for focus moving in and out, refs() to focus a computed element, timer() for a toast or a debounce, and when to branch. Key names and timer delays are checked by types where they can be and at run time otherwise. Signals are for state that only the browser decides, such as whether a panel is open. Copying server data into signals and changing it there is not recommended, because the data then has two owners. Browser signals

Showing the user's own action as pending

This is not recommended in most cases: the pending state that the runtime shows while a request is in flight is enough. Use it only where it is truly needed, such as dragging, frequent personal toggles, and sending your own text.

A page does not predict the server's result: new row keys, totals, stock, or the outcome of other people's edits appear once the server commits them. It may show the user's own action before it is confirmed, as a pending echo: the favorite they just toggled, the position they dropped an item at, or the chat text they just sent. Use it for direct manipulation such as dragging, for frequent low-stakes personal toggles where a round trip of more than about 300 ms feels broken, and for sending your own text. Do not use it for values other people edit at the same time, values the server decides (keys, prices, stock, permissions), input that validation may reject, or actions that cannot be undone, such as payments; show the pending state alone for those.

A pending echo follows three rules:

  1. Mark the shown value as pending: style the data-hs-pending attribute the runtime puts on the sending control, and show text with action.pending() for assistive technology.
  2. On failure, set the latest committed value, not the value from before the click. A commit from another tab can arrive while the request is in flight.
  3. Let the committed value from the Live View replace the echo.

action.call(input, { pending }) follows rules 2 and 3 for you. pending lists set statements that write the shown value when the call runs. The runtime remembers the latest committed value of each path from the Live View, lets a committed value replace the shown one at any time, and writes the latest committed value back when the request fails. The value must come from a Live View, and the Action must publish the Topic that renders it again. The favorite button in the Widgets example is written this way. Browser signals

Connection recovery

The server associates displayed View keys with the authenticated page. A reconnect reads the current state again. Access is checked when the View is rendered and again before updates are sent.

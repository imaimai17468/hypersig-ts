Migrating from htmx

htmx and hypersig.ts both render HTML on the server. They differ in where updated HTML comes from: in htmx, the response to a request is swapped into a target; in hypersig.ts, an Action changes data and publishes a Topic, and every Live View subscribed to it renders again and arrives over SSE.

The change in the model

An htmx element names a URL, a target selector, and a swap strategy, and the server answers that one request with the fragment to insert. Other parts of the page, and other tabs, change only if the response says so.

In hypersig.ts, the Action response reports only success or failure and the Action's output. After it commits, the Action publishes a Topic. Each Live View declares the Topics it depends on, so the server renders exactly the views that subscribed, in every open page, and the browser morphs them into place. The page that sent the Action receives its update the same way as every other page.

The names an htmx page repeats as strings (URLs, field names, target IDs, event names) are values in hypersig.ts. An Action is referenced through the object hypersig.action() returned, so a renamed Action, a misspelled form field, or an input of the wrong shape is a type error rather than a request that fails at run time.

Concept map

hx-post, hx-get
An Action: action.bind(input) on a button, action.form() on a form, or action.call(input) in signal statements. Actions are POST requests; read data by rendering a page or a Live View.
hx-target, hx-swap
A Live View boundary placed with page.view(view, props). The whole view renders on the server and is morphed into place, which keeps focus and unfinished input. There are no swap modes such as beforeend; render the full list in the view instead.
hx-swap-oob
Several Live Views subscribed to the same Topic. Publishing it once updates all of them.
hx-vals, hx-include
Typed input passed to bind() or call(), or the form's fields, named with action.field().
hx-trigger
on.click, on.input, on.change, on.keydown, on.focusEnter, and on.focusLeave. A delay: modifier becomes a timer() whose after() restarts on each event. Instead of polling with every 2s, publish a Topic when the data changes.
hx-indicator, htmx-request
The data-hs-pending attribute on the sending form or button, or the action.pending() signal.
hx-sync, hx-disabled-elt
A form or button with a request in flight is not sent again. Disable other controls with bindAttr({ disabled: action.pending() }).
SSE extension
Built in. Each page opens one stream that carries the updates of all its views, reconnects on its own, and reads the current state again when it does.
hx-boost, hx-push-url
Ordinary links. Following one loads the next page from the server; there is no client-side navigation or history handling. Build links with Hono's typed $path().
Alpine.js, _hyperscript
Signals for state only the browser decides, such as an open menu or an input's value. A JavaScript library or a React component goes in a custom element.
Error responses
action.fieldError(name) for a field's validation message and errorOutlet() for an Action's failure message.

A button that updates a region

The htmx server route returns the new #counter fragment. In hypersig.ts, execute returns a number, and the HTML comes from counter, which renders again in every page that shows it because it subscribes to counterChanged().

Active search

The Action stores the query on the server and publishes a Topic keyed by the session, so the results follow the session's latest query in each of its tabs. searchDelay.after(300, ...) cancels the previous reservation on every input, as delay:300ms does. To filter items that are already on the page without a request, bind bindShow to an expression such as lit(name).includes(s.q) instead.

Loading indicators

data-hs-pending stays until the last request from that control ends, even when a Live View update arrives first. Values on the page change when the committed update arrives, not when the request is sent.

Out-of-band swaps

The Action does not need to know which parts of the page show notes. A note list view and noteCount both subscribe to notesChanged(), and a background job that publishes the same Topic updates them too.

Forms and validation errors

<form {...addNote.form({ resetOnSuccess: true })}>
  <input name={addNote.field("text")} />
  <p {...addNote.fieldError("text")}></p>
  <button type="submit">Add</button>
  <p role="alert" {...errorOutlet()}></p>
</form>

addNote.field("text") checks the name against the input schema. The server validates the submission; the runtime writes a field's message into the element marked with fieldError and an Action's failure into errorOutlet(). To accept a form posted without JavaScript, define formResponse on the Action to render a page or redirect.

Content Security Policy

htmx evaluates hx-on handlers, trigger filters, and js: values with eval, so a policy without 'unsafe-eval' needs htmx.config.allowEval = false, which turns those features off. The standard Alpine.js build also needs 'unsafe-eval'.

The hypersig.ts runtime is one script served from your origin. Signal expressions and statements are JSON that it interprets, so pages work under script-src 'self' without 'unsafe-eval' or inline scripts. Live View HTML is sanitized with DOMPurify before it enters the page. The examples send default-src 'none'; script-src 'self'; connect-src 'self'.

What works differently

  • Live updates need JavaScript and an open SSE connection. Without them the page shows its server-rendered HTML, and a form posted natively gets an HTML response only from an Action that defines formResponse; any other Action answers with JSON.
  • An update replaces a whole Live View. Split the page into views by what changes together, and keep large lists that rarely change outside the frequently updated view.
  • Views load from server state. A value that exists only in one request, such as a search query, has to be stored on the server, as in the active search example.
  • Each Live View and Action checks access itself with authorize. hypersig.page() answers 401 when authenticate returns null, so give anonymous visitors a session too, each with its own id.

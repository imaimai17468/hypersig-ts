API reference

Use these APIs to handle actions on the server, publish changes, and update parts of a page.

What TypeScript checks

  • Actions check button inputs and the form field names passed to action.field() against the input schema. The server validates submitted values and action results.
  • Change notifications use the same type for publishers and subscribers. The write operation declares which change to publish.
  • Views that update check the arguments passed from the page and the values passed from the loader to the renderer.

Hono adapter

Use createHypersig in a Hono app. To supply your own renderer and connection handling, use hypersig.ts/core.

createHypersig(options)
Set the public origin, session authentication, and Pub/Sub implementation.
hypersig.routes
Mount the Action and SSE endpoints on the Hono application after registering Actions.
hypersig.page(request, render)
Authenticate the request and render the page as HTML.

Typed links

Create hc<typeof app>("/") from the Hono routes and pass the result of $path() to href in server-rendered JSX. Hono checks the path parameter names and the query types inferred from the route validator when you build the link. 

const links = hc<typeof app>("/");
const href = links.counters[":counterKey"].$path({
  param: { counterKey: "main" },
  query: { view: "display" },
});

The Counter example uses Valibot to validate the received key and view mode. Server example · Hono typed paths

Actions

Use hypersig.action(name, definition) with a literal name of letters, digits, _, or -, Standard Schema input and output definitions, an authorize check, and an execute function. 

<button type="button" {...increment.bind({ counterId: "main" })}>
  Increment main
</button>

action.bind(input) binds typed data to a button and sends it as JSON, so an input type that is not JSON, such as one with a Date, is a type error there. action.form() supplies attributes for an HTML form. The Action response reports the result. Subscribed Views update over SSE. 

<form {...increment.form()}>
  <input type="hidden" name={increment.field("counterId")} value="main" />
  <button type="submit">Increment</button>
</form>

action.field(name) checks that the name belongs to a top-level field in the input schema and returns it as an HTML field name. The server validates submitted values when it receives the form.

Live Views

name
Optional. Starts the view's key in the page, such as counter-1. The runtime numbers each definition, so two definitions never share a key. A literal name with characters other than letters, digits, _, or - is a type error.
key
Optional. Tells apart instances of the same definition under one parent, such as counter-1.main and counter-1.other.
subscribe
Returns the Topics that affect this view.
authorize
Checks that the session can see this view.
load
Reads the data to display.
render
Converts the data to HTML.

Use page.view(view, props) to place the boundary in the document.

Browser signals

Signals hold state that only the browser decides, such as a toggle or an input value. Define a group with signals(initial, { name }), or one group per key, such as a row, with signalFamily(initial, { name }).at(key). Values must be JSON. Expressions are data that the browser runtime evaluates, so the page needs no eval and works under script-src 'self'. 

const editor = signals(
  { base: 0, published: 0, operation: "" },
  { name: "memo-editor" }
);
const e = editor.with({ base: draft.revision });
with(values)
Returns a handle that renders attributes with these values for the current request. init() writes the fields passed to with as values the server owns, and the other fields as defaults. A default applies only when the browser has no value for the signal, so a Live View update never overwrites a browser-only value. Fields passed to with replace the browser's value when a Live View update arrives.
Bindings
bindText(expr), bindShow(expr), bindAttr({ ... }), and bindValue(signal) return attributes to spread into JSX. The server evaluates the expression and renders the result, so the first paint is correct. bindAttr accepts disabled, checked, aria-pressed, aria-expanded, aria-current, aria-hidden, aria-invalid, aria-busy, and data-* other than data-hs-*. It rejects href, src, on*, and style in the type and at run time. bindValue binds a text, number, or checkbox input to a string, number, or boolean signal. It also binds a hidden input, so a signal can decide the value a form submits. The runtime reads a bound hidden input when it starts, so a value restored from a draft replaces the rendered one.
Expressions
Every signal is an expression. All have eq and ne. A number has add, sub, mul, gt, ge, lt, and le. A boolean has not, and, or, and choose(whenTrue, whenFalse). A string has concat. lit(value) and uuid() create values.
on.click(stmts)
Also on.input and on.change. Runs statements in order: signal.set(expr), signal.toggle() for a boolean, draftRef.focus(), and action.call(input). const draftRef = ref({ name }) creates a ref, and {...draftRef.attr()} names the element that draftRef.focus() moves focus to.
action.call(input, options)
Sends the Action from a statement. Each input field takes a value or an expression. Writes made before the call in the same handler show at once. If the Action fails and no Live View update has written the path since, the runtime restores the previous value. While the call is in flight, a Live View value for those paths waits until the call ends. options.onSuccess(output) and options.onError take statements. action.form() accepts the same two options.
action.pending() and action.draftRestored()
Built-in signals. pending() is true while a request to the Action is in flight. draftRestored() is true after a saved draft was restored into the Action's form({ draft: true }), and false again once that Action succeeds.
action.form({ onSubmit })
Runs statements in the browser when the form is submitted, before the request is sent. Writes made there are owned by the submit request, like the writes before a call. A form with onSubmit can be submitted again while an earlier request is in flight; each request owns its own writes and previews, and pending() and the form's data-hs-pending attribute stay set until the last request ends. A form without onSubmit sends one request at a time and ignores a submit while its request is in flight.
insertTemplate(initial, { name })
Defines a row template for an optimistic list insert. Define it at module level, because the ID name-number is assigned when it is called. initial sets the field types, and item.field is the expression for a field of the inserted row. The template has these parts:
  • template() goes on a <template> element. Its content must have exactly one root element, and the template must sit outside every Live View, because DOMPurify strips <template> elements from a fragment. The bind methods (bindText, bindShow, bindAttr) render item with the initial values on the server and with the inserted values in the browser. Use item only with these methods inside the template: elsewhere nothing reports a mistake, another scope's bind methods render it as false on the server, and in the browser it has no value outside a preview.
  • slot() goes on the list element the browser inserts into. Put it inside the Live View that renders the confirmed rows, and only on lists the item will join. If the slot's Live View never receives the confirmed row, or the slot is outside every Live View, a successful preview stays until the page reloads.
  • insert(values, key) is a statement. It appends a preview row to every slot of the template. A value is a literal or an expression, and key is a string or a string expression. The compiler checks the field names only through types, so a caller without types gets no error for an unknown field.
  • confirms(key) goes on the confirmed row. When an element with confirms(key) appears anywhere in the Live View that holds the slot (not in a nested Live View), the preview for that key is removed. A failed Action also removes it. 
<button
  type="button"
  {...r.bindAttr({ "aria-pressed": r.completed })}
  {...on.click([
    r.completed.toggle(),
    toggle.call({ todoKey: todo.key, completed: r.completed }),
  ])}
>
  <span {...r.bindText(r.completed.choose("✓", "○"))} />
</button>

An optimistic add chains these. The browser creates the key, shows the preview, and sends the key in the Action input. The server validates the key format, rejects a key that already exists, and renders the confirmed row with confirms(key). The browser replaces the key before each send, so the hidden input's server-rendered value is only for a form posted without JavaScript; give it a fresh key per request, or a native submit fails key validation. 

const newTodo = insertTemplate({ title: "" }, { name: "new-todo" });
const composer = signals({ title: "", key: "" }, { name: "composer" });
const entry = composer.with({ key: crypto.randomUUID() });

<form
  {...entry.init()}
  {...add.form({
    resetOnSuccess: true,
    onSubmit: [
      entry.key.set(uuid()),
      newTodo.insert({ title: entry.title }, entry.key),
    ],
  })}
>
  <input type="hidden" name={add.field("todoKey")} {...entry.bindValue(entry.key)} />
  <input name={add.field("todoTitle")} {...entry.bindValue(entry.title)} />
</form>

<ul {...newTodo.slot()}>
  {todos.map((todo) => (
    <li {...newTodo.confirms(todo.key)}>...</li>
  ))}
</ul>

<template {...newTodo.template()}>
  <li><span {...newTodo.bindText(newTodo.item.title)} /></li>
</template>

The confirmed list belongs to the Live View, and the browser draws only the preview. During a Live View morph, previews are detached and appended again at the end of their slot. A preview whose slot disappeared in the morph is dropped, and focus inside a preview is lost. If the Action fails, the preview is removed. A preview cannot be reordered or edited.

Deleting needs no new API. Give the row a signal with a removed field, hide it with bindShow(r.removed.not()), and set it before the call: on.click([r.removed.set(true), remove.call({ todoKey: todo.key })]). A failed call restores the field and shows the row again.

Known limitations

  • An optimistic value can flash back. This happens when a Live View update with the value from before the commit arrives while the call is pending, then the response arrives, then the update after the commit arrives.
  • Calls from different controls that overlap on the same path can restore the other call's optimistic value when one of them fails. The next Live View update corrects it.
  • The detail.data of the hypersig:action-success event is null when the response has no data, where it was undefined before.

API reference

Use these APIs to handle actions on the server, publish changes, and update parts of a page.

What TypeScript checks

  • Actions check button inputs and the form field names passed to action.field() against the input schema. The server validates submitted values and action results.
  • Change notifications use the same type for publishers and subscribers. The write operation declares which change to publish.
  • Views that update check the arguments passed from the page and the values passed from the loader to the renderer.

Hono adapter

Use createHypersig in a Hono app. To supply your own renderer and connection handling, use hypersig-ts/core.

createHypersig(options)
Set the public origin, session authentication, and Pub/Sub implementation.
pageKeys
Optional. An array of keys that encrypt page registrations, each a base64 (or base64url) string of 32 bytes. The first key encrypts and every key is tried to decrypt. When omitted, the keys are random per process, so set it to continue pages across restarts or to run multiple instances.
onDiagnostic
Optional. Receives events about publishing, rendering, and opening pages. page-token-invalid reports a token that was altered or encrypted with a key the runtime does not hold. Any client can cause it by sending a broken token, so do not alert on a single event. page-rebuild-failed reports, in view, the name of a view in a valid token that is no longer registered, or whose key() throws or returns an invalid or duplicate key. Both get reset and fetch the page again.
pageLifetimeMs
Optional. How long a page token is valid in milliseconds, counted from when the HTML is rendered or the token was renewed. Defaults to 12 hours. Each reconnect at maxStreamMs carries a renewed token while the user can still read every top-level view on the page, so a connected page keeps receiving updates past expiry. A connection made after the page's last token expired gets reset and fetches the page again.
pageContext
Optional. A string that names the application and environment, bound into every page token. A token opens only in a runtime with the same context, so apps or environments that share pageKeys and sessions cannot use each other's tokens. Defaults to the normalized origin. When one app serves several origins, give every instance the same value. A token from another context gets reset and a page-token-invalid diagnostic.
maxStreamMs
Optional. How long one SSE stream stays open in milliseconds. Defaults to 30 minutes. Each stream ends at a random time between 90% and 100% of this value with a reconnect event, and the browser runtime opens a new stream at once without reloading or showing the page as disconnected. The new request carries the browser's current credentials. Until then, the stream authenticates with the request it opened with. Right before reconnect, the server authenticates the stream's user again. If they are in the same session and can still read every top-level view on the page, the event carries the page token sealed again with a new pageLifetimeMs, keeping the views, params, and SSR snapshots, and the browser opens the next stream with it. Otherwise it carries no token, and the browser reopens with the token it has. The server waits at most sendTimeoutMs for that check, and past it ends the stream without a token, so a stalled authenticate or authorize cannot keep a stream open longer. The browser accepts only data shaped like a page token, which replaces the last path segment of the stream URL, so the stream never moves to another path or origin.
maxStreamsPerSession
Optional. How many streams one session can hold open in one process. Defaults to 16. One more stream sends evicted to the session's oldest stream and closes it. That page keeps its views, stops live updates, and sets the connection status to too-many-tabs until it is reloaded. Unless the page renders connectionStatusOutlet(), only data-hs-connection changes, so render the outlet to tell the user. The count is per process, so also rate-limit page renders and /_hypersig/stream/*. Sessions that share a sessionId, such as "anonymous", share one count, so give every session its own id. Send frame-ancestors (or X-Frame-Options) and set session cookies SameSite=Lax or Strict, so a cross-site page cannot open your pages in frames that evict the user's tabs; Strict also keeps a popup another site opens from carrying the session.
hypersig.routes
Mount the Action and SSE endpoints on the Hono application after registering Actions.
hypersig.page(request, render)
Authenticate the request and render the page as HTML.

Typed links

Create hc<typeof app>("/") from the Hono routes and pass the result of $path() to href in server-rendered JSX. Hono checks the path parameter names and the query types inferred from the route validator when you build the link. 

const links = hc<typeof app>("/");
const href = links.counters[":counterKey"].$path({
  param: { counterKey: "main" },
  query: { view: "display" },
});

The Counter example uses Valibot to validate the received key and view mode. Server example · Hono typed paths

Actions

Use hypersig.action(name, definition) with a literal name of letters, digits, _, or -, Standard Schema input and output definitions, an authorize check, and an execute function. 

<button type="button" {...increment.bind({ counterId: "main" })}>
  Increment main
</button>

action.bind(input) binds typed data to a button and sends it as JSON, so an input type that is not JSON, such as one with a Date, is a type error there. action.form() supplies attributes for an HTML form. The Action response reports the result. Subscribed Views update over SSE. 

<form {...increment.form()}>
  <input type="hidden" name={increment.field("counterId")} value="main" />
  <button type="submit">Increment</button>
</form>

action.field(name) checks that the name belongs to a top-level field in the input schema and returns it as an HTML field name. The server validates submitted values when it receives the form.

The runtime writes messages into elements you mark. action.fieldError(name) marks the element in the form that shows the schema's message for one field after a failed submission. errorOutlet() marks where an Action's failure message goes, using the one inside the submitting form first, and connectionStatusOutlet() marks where the page says that live updates disconnected. Spread each on the element, as in <p role="alert" {...errorOutlet()} />.

The runtime writes the connection status to data-hs-connection on <html>: connecting, ready, disconnected, reload-required, or too-many-tabs. The connection status outlet shows a message for disconnected, reload-required, and too-many-tabs. When the server answers reset, the runtime saves drafts and reloads the page, at most 3 times within 60 seconds in one tab. After that, or when sessionStorage is not available, it clears the views, keeps the form contents, and sets the status to reload-required instead of reloading. too-many-tabs means the server evicted the page's stream because the session has more than maxStreamsPerSession streams open. Only the outlet tells the user about it: without connectionStatusOutlet(), the page just stops updating and changes data-hs-connection, so render the outlet on every live page.

action.control(name) returns the field name together with constraint attributes read from the input schema: required, minLength, maxLength, pattern, min, and max. Spread it onto the control: <input {...add.control("title")} />. It appears in the type only when the input schema also implements Standard JSON Schema, for example when it is wrapped with toStandardJsonSchema() from @valibot/to-json-schema; for any other schema it is a type error. The schema is converted to JSON Schema once, on the first call. No type is emitted. A field the converted schema does not describe returns only its name.

The derived attributes never make the browser stricter than the server. Where an attribute could reject a value the server accepts, it is left out:

  • required is set only for a field the schema requires that is not a boolean and whose schema rejects the empty string: a minLength of at least 1, a pattern that does not match "", or an enum without "". A required v.string() accepts "", so it gets no required.
  • pattern is set only when the expression starts with ^, ends with an unescaped $, has no top-level |, and compiles with the v flag, because the browser checks ^(?:pattern)$ with that flag. pattern has no effect on <textarea>.
  • min and max appear only when the input-side schema is a number. Form posts are strings, so a form field that converts with toNumber() or transform() yields neither.

If conversion fails, control() throws an error that names the Action. Pass jsonSchema: { libraryOptions } to createHypersig to skip parts that have no JSON Schema form, such as { ignoreActions: ["trim"] } for Valibot's v.trim(). Constraints written after a skipped action are checked in the browser against the raw value, so skip only actions that do not change what those constraints mean. Avoid { errorMode: "ignore" }: it drops a regular expression's flags and keeps its pattern, so the browser checks a different expression. The message a user sees before submission is the browser's own; the server's schema messages appear only after the server validates.

Live Views

name
Required. The view's key in the page, such as counter. It must be unique in the runtime, and a duplicate throws when the view is defined. A literal name with characters other than letters, digits, _, or - is a type error. Define views with hypersig.live(); there is no standalone live().
key
Optional. Tells apart instances of the same definition under one parent, such as counter.main and counter.other.
subscribe
Returns the Topics that affect this view.
authorize
Checks that the session can see this view.
load
Reads the data to display.
render
Converts the data to HTML.

Use page.view(view, props) to place the boundary in the document. The props of a top-level page.view must be JSON values.

Browser signals

Signals hold state that only the browser decides, such as a toggle or an input value. Copying server data into signals and changing it there is not recommended, because the data then has two owners. Define a group with signals(initial, { name }), or one group per key, such as a row, with signalFamily(initial, { name }).at(key). Values must be JSON. Expressions are data that the browser runtime evaluates, so the page needs no eval and works under script-src 'self'. 

const editor = signals(
  { base: 0, published: 0, operation: "" },
  { name: "memo-editor" }
);
const e = editor.with({ base: draft.revision });
with(values)
Returns a handle that renders attributes with these values for the current request. init() writes the fields passed to with as values the server owns, and the other fields as defaults. A default applies only when the browser has no value for the signal, so a Live View update never overwrites a browser-only value. Fields passed to with replace the browser's value when a Live View update arrives.
Bindings
bindText(expr), bindShow(expr), bindAttr({ ... }), and bindValue(signal) return attributes to spread into JSX. The server evaluates the expression and renders the result, so the first paint is correct. bindAttr accepts disabled, checked, aria-pressed, aria-expanded, aria-current, aria-hidden, aria-invalid, aria-busy, aria-activedescendant, aria-selected, aria-controls, aria-label, tabindex, hidden, and data-* other than data-hs-*. It rejects href, src, on*, and style in the type and at run time. disabled, checked, and hidden are present while the value is truthy. The others render the value as text, and a null value leaves the attribute out, so open.choose<string | null>(id, null) names an aria-activedescendant only while open. bindValue binds a text, number, or checkbox input to a string, number, or boolean signal. It also binds a hidden input, so a signal can decide the value a form submits. The runtime reads a bound hidden input when it starts, so a value restored from a draft replaces the rendered one.
Expressions
Every signal is an expression. All have eq and ne. A number has add, sub, mul, gt, ge, lt, and le. A boolean has not, and, or, and choose(whenTrue, whenFalse). A string has concat. lit(value) and uuid() create values. A string also has length(), trim(), lower(), and includes(other). A number has clamp(min, max) and mod(n), which wraps into 0 up to n. An array has at(index, fallback) and length(). A value of the wrong type does not throw: length() gives 0, trim() and lower() give an empty string, includes gives false, mod(0) gives 0, clamp gives min when the value or max is not a number and 0 when min is not a number, and an out-of-range at gives fallback. length() is the UTF-16 length, so an emoji counts as 2.
on.click(stmts)
Also on.input and on.change. Runs statements in order: signal.set(expr), signal.toggle() for a boolean, draftRef.focus(), and action.call(input). const draftRef = ref({ name }) creates a ref, and {...draftRef.attr()} names the element that draftRef.focus() moves focus to.
on.keydown(map)
Takes a map from keys to statements, runs the statements for the key that was pressed, and prevents its default action. Write keys as KeyboardEvent.key values: a named key (Enter, Escape, Tab, " ", the arrows, Home, End, PageUp, PageDown, Backspace, Delete), one character, or a number. A number key is one digit, "0" to "9", so 10 is a type error and throws. Modifiers go in front in the order Control+, Alt+, Shift+, Meta+. A wrong name or order is a type error, and a computed name the type cannot check throws when on.keydown is called.
  • Modifiers must match exactly (Enter does not match Shift+Enter). Without Control, Alt, or Meta, a one-character key other than Space ignores Shift: "?" and "A" match with or without Shift, and "Shift+?" is a type error and throws. With Control, Alt, or Meta, Shift counts and the character is compared in either case, so write it in lowercase: "Control+z" matches only without Shift, "Control+Shift+z" and "Shift+Meta+z" only with it, and "Control+Z" is a type error and throws.
  • The runtime searches from the element that was pressed outward and uses the first map that has the key. Tab and Shift+Tab keep their default action. A keydown during IME composition is ignored.
  • While an Action is sending from the element that holds the map, the key's default action is prevented but the statements do not run.
  • A key whose default an element inside already prevented, such as an island that handles it, runs no map. A map inside a custom element that renders its own children is ignored.
  • Some limits are not checked by types. Caps Lock changes the case of a letter typed without Control, Alt, or Meta. A symbol that needs Shift on the keyboard layout, such as "?" on a US layout, matches with Control only as "Control+Shift+?". macOS Option composes characters, so Alt+<letter> may never arrive. Mapping Enter or " " on a container stops the buttons inside from activating, and mapping one character stops that character from being typed in the inputs inside.
on.focusEnter(stmts) and on.focusLeave(stmts)
Run statements when focus moves into the element from outside, or out of it. Moves inside the element do not run them. When the page loses focus because the window or tab switched, focus is not treated as having left; it counts as leaving when focus returns somewhere else. Pressing the mouse on an element inside moves focus to body first, so give the elements that are pressed tabindex="-1". Without it, focusLeave runs. They do not run while the element is sending.
refs({ name })
Focuses the element for a computed key. Put {...tabRefs.attr(key)} on each element, and the statement tabRefs.focus(keyExpr) moves focus to the element whose key is the expression's value. The key is a string or a string expression; a number, boolean, or array expression is a type error. It does nothing when no element matches. ref() and refs() both write data-hs-ref, so give an element only one of them; when both are spread, the later one wins. focus() finishes a pending render first, so it reaches an element that an earlier set in the same statements un-hid.
when(condition, then, otherwise)
Runs then when the condition is true and otherwise (nothing when omitted) when it is false. Truth is decided as in choose. It works wherever statements do, and a call in a branch is sent from the element that ran when.
timer({ name })
Creates a named timer. Define it at module scope. t.after(ms, stmts) cancels the previous reservation and reserves the statements to run after ms milliseconds. Calling it again restarts the count, which makes a debounce. t.cancel() cancels the reservation.
  • There is one reservation per timer on the page, and it survives a Live View update that removes the element.
  • ms is an integer from 0 to 2147483647. The type is number, and a value outside that range throws a RangeError.
  • If the element that scheduled it has left the page, a call is not sent and the other statements still run.
  • The statements run when the time comes even while the scheduling element is sending, so the same Action can be sent concurrently.
  • The statements read the output and detail from the time they were scheduled.
action.call(input, options)
Sends the Action from a statement. Each input field takes a value or an expression. options.onSuccess(output) and options.onError take statements. action.form() accepts the same two options. options.pending takes set statements that show a value until the Action is committed (see Showing a value before it is confirmed below).
action.pending() and action.draftRestored()
Built-in signals. pending() is true while a request to the Action is in flight. draftRestored() is true after a saved draft was restored into the Action's form({ draft: true }), and false again once that Action succeeds.
data-hs-pending
The runtime sets this attribute on the form or button that sent a request and removes it when the last request that control sent ends, whether it succeeded or failed. A Live View update does not remove it while a request is in flight. A control with a request in flight is not sent again. CSS can use the attribute to show progress without JavaScript.
action.form({ onSubmit })
Runs statements in the browser when the form is submitted, before the request is sent. Bindings are rendered again before the form data is built, so a hidden input bound to a signal sends a value the statements wrote. Writes made there stay when the request fails, like the writes before a call. A form whose request is in flight is not submitted again, and its statements do not run.

The page reacts to an action at once and shows data once the server has confirmed it. While a request is in flight, show that it is in progress with pending() or data-hs-pending; the values on the page change when the Live View update with the committed data arrives. New list rows come from the server too, in that update. TodoMVC dims a row while its toggle or delete is in flight: 

<button
  type="button"
  aria-pressed={String(todo.completed)}
  {...toggle.bind({ todoKey: todo.key, completed: !todo.completed })}
>
  {todo.completed ? "✓" : "○"}
</button>

/* style.css */
li:has(.row [data-hs-pending]) {
  opacity: 0.55;
}

The selector looks only inside the row's .row element, so a pending edit form in the row's popover does not dim the row.

Showing a value before it is confirmed

This is not recommended in most cases: the pending state is enough. Use it only where it is truly needed, such as dragging, frequent personal toggles, and sending your own text. A write before a call is an ordinary write: it shows at once and stays when the Action fails. To show the user's own action until the server confirms it, as in Showing the user's own action as pending, pass set statements as options.pending: 

const f = favoriteState.with({ favorite });
on.click(
  saveFavorite.call(
    { favorite: f.favorite },
    { pending: f.favorite.set(f.favorite.not()) }
  )
)
  • The statements run when the call runs, and the input is evaluated after them, so the Action receives the value they wrote. The sending control has data-hs-pending as for any call.
  • pending takes set statements only. Its type accepts any statement, and call() throws a TypeError for any other statement.
  • Each path needs a committed value: a field passed to with whose init() is rendered, usually by a Live View. The runtime keeps the latest such value of each path from the first page and every Live View update, one value per path. When a path has none, the handler that runs the call throws (a click, a key, a timer, a custom event, a focus move, onSubmit, or the result statements of another call), sends nothing, and runs none of its later statements. The exception reaches the window's error event.
  • A Live View update during the request replaces the shown value at once, except on the path of a focused bindValue text input. When the request fails, the runtime writes the latest committed value back to each path that still shows the pending value, then runs onError. It does not write back the value from before the click, which is stale once a commit from another tab has arrived during the request.
  • When a later call writes the same path before the earlier one ends, the path follows the later call: the earlier call's failure leaves it alone, and the later call's failure writes the committed value back. A set or toggle statement, or a bindValue input, that writes the path during the request ends the pending value, so a failure keeps that newer write, such as a slider the user moved on. A Live View update does not end it.
  • A success leaves the shown value as it is. The Action must publish the Topic that renders the value again; otherwise the sent value stays until the next update.

Do not show values early that other people may edit at the same time, values the server decides (such as keys, order, or totals), or input that may fail validation; show the pending state instead.

Known limitations

  • bindAttr removes a non-boolean attribute only when the expression evaluates to null. When it becomes an empty string, the attribute stays with an empty value (aria-activedescendant="").
  • The detail.data of the hypersig:action-success event is null when the response has no data, where it was undefined before.

Custom elements

Wrap a JavaScript library, such as a map or an editor, in a custom element. You declare the element's attributes and events once, as a value. The page sets the attributes and handles the events from that value, and the browser-side code is typed by the same value, so none of them is written as a string literal. 

// elements.ts, imported by the server and the browser
import { customElement, event } from "hypersig-ts/element";

export const rating = customElement("star-rating", {
  attributes: { value: "number", max: "number" },
  events: { rate: event<number>() },
  ownsChildren: true,
});

// server
<CustomTag
  of={rating}
  id="rating"
  {...e.bindElement(rating, { value: e.score, max: 5 })}
  {...rating.on("rate", (detail) => [
    e.score.set(detail),
    save.call({ score: detail }),
  ])}
/>
customElement(tag, { attributes, events, ownsChildren })
Returns the declaration. attributes maps each name to "string", "number", "boolean", or json<T>(). events maps each name to event<Detail>(). T and Detail must be JSON values. The tag name starts with a lowercase letter, contains a -, and has only lowercase letters, digits, -, ., and _. The type checks what it can, and the rest is checked when customElement is called, as are attribute and event names and kinds, so a typo is an error at startup. The names HTML reserves, such as font-face and annotation-xml, are rejected the same way. An attribute name must be lowercase and must not start with on (this rejects once too), nor be style, id, or data-hs-*. A data-* attribute cannot be json. An event name starts with a lowercase letter and then has lowercase letters, digits, -, ., :, or _. It cannot be click, input, change, or submit, which the runtime handles for every element; the type rejects these names, and the runtime ignores them in a hand-written data-hs-on-custom. The function and the types are exported from hypersig-ts/element, which imports neither Hono nor React and can be imported where there is no DOM, and from hypersig-ts.
<CustomTag of={declaration} />
Renders the element with the declared tag name. It takes the HTML attributes Hono JSX names, role, part, exportparts, aria-*, data-*, children, and the declared attributes as fixed values. A json attribute takes any JSON value of its type, read-only arrays included, and is written as JSON.stringify text. A value that is not JSON, such as NaN or one nested more than 64 levels deep, throws a TypeError. When a prop and bindElement write the same attribute, the later one wins. CustomTag leaves alone only the exact text bindElement wrote for an attribute, and encodes every prop value, strings included. A true value renders the attribute empty and false leaves it out, except for aria-*, data-*, draggable, spellcheck, and contenteditable, whose booleans render as "true" or "false". When the declaration sets ownsChildren: true, id is required (a type error otherwise). In a list give each element an id of its own: a Live View update keeps an element that owns its children only when the tag and the id match, and rebuilds it otherwise, which loses what the element's JavaScript held.
scope.bindElement(declaration, values)
Binds the declared attributes to expressions. The server renders the first value, and the runtime writes later ones as the signals change. It writes data-hs-element-attr and keeps its own rule: it takes any declared name that passes the attribute rules above, and writes a string or number as text, a json value as JSON.stringify text, and a boolean as CustomTag does: an empty or absent attribute, or "true" or "false" for the names listed there. It writes an attribute only when its value changes (for a json attribute, when the text changes), so attributeChangedCallback does not run for changes to other signals. id cannot be bound: an owned element whose id changes is rebuilt, so give it a fixed id from the server render. bindAttr keeps the name list and data-hs-attr described under Bindings. The type checks the declared keys and their value types, but an object from a variable that has extra keys still writes them, and the runtime checks only the name rules at run time.
declaration.on(event, handler)
Runs statements when the element dispatches the event, with detail standing for the event's detail as an expression of the declared type. To handle several events on one element, pass one object, rating.on({ rate: ..., clear: ... }); spreading two results keeps only the later one. A call in the handler can use detail in its onSuccess and onError statements too. The runtime runs these events even while a request from the same element is in flight, so rapid events are not dropped and can send overlapping calls. It starts listening on the next render after the element is inserted, so an event dispatched synchronously in connectedCallback runs nothing.
ownsChildren
Set it when the element's JavaScript renders its children. A Live View update then keeps the children and updates only the element's attributes. Attributes named in bindElement are left to the runtime during that update, so the element does not see a transient server value in attributeChangedCallback; a bound attribute the server meant to change waits for the runtime to render it again, within the same tick. Attributes the server rendered as fixed values, including json ones, are copied as usual. The runtime ignores hypersig attributes inside those children, such as bindings, on.click handlers, snapshots, value bindings, refs, custom event handlers, Action buttons, action.form() forms, error outlets, and draft fields, because the element's JavaScript may render user content there. Such a button or form sends nothing and a form does not post natively either. An event inside the children runs the nearest handler on the element itself or outside it. Put them on the element itself or outside it. Without ownsChildren, children the element's JavaScript renders are removed by the next Live View update.

Implementing the element: defineElement

import { defineElement } from "hypersig-ts/element";

defineElement(rating, {
  mount(host, props, emit) {
    // props: { value?: number; max?: number }
    // emit("rate", 3) is checked against the declaration
    return {
      update(props) {},
      unmount() {},
    };
  },
});
  • It calls customElements.define with the declared tag and throws if that tag is already defined.
  • mount runs when the element is inserted. Each declared attribute is read as its kind and is left out of props, so it reads as undefined, when it is absent or cannot be read: a number that is not a finite number, a text boolean (data-*, aria-*) that is not "true" or "false", or a json value that JSON.parse cannot read or that nests more than 64 levels deep. A number is read with Number(), so "0x10" and "1e3" read as numbers, and an empty string does not. A json value is not checked against its declared type, so treat it as input.
  • Attribute changes made in one task reach update once, in a microtask, with every declared attribute read again. A change made before unmount never reaches update.
  • unmount runs when the element is removed. Inserting the same element again calls mount again, so moving an element calls unmount and then mount.
  • If mount throws, the element stays unmounted: neither update nor unmount runs, and it is mounted again only when it is inserted again.
  • emit(name, detail) dispatches a CustomEvent that does not bubble, which the handlers from declaration.on receive.

The types check props and emit against the declaration only for an element written with defineElement. An element you register yourself with customElements.define is not compared with its declaration at all.

React islands

import { reactElement } from "hypersig-ts/react";

reactElement(sortableList, SortableList);
// SortableList: (props: { items?: Item[]; failures?: number; emit: Emit<...> }) => ReactNode

reactElement(declaration, Component) is built on defineElement. Insertion creates a React root on the element and renders Component with the declared attributes (optional, as in props above) and emit. An attribute change renders into the same root, so the component keeps its state. Removal unmounts the root from disconnectedCallback; if an outer React tree removes the element during its commit, React warns about unmounting a root while it is rendering, but a server-rendered page does not have an outer React tree. A component whose props do not match the declaration is a type error, and so is a declaration without ownsChildren: true, because React replaces the children. react and react-dom (^19) are optional peer dependencies, needed only by apps that import hypersig-ts/react. An island is not rendered on the server: the server's HTML holds only the placeholder children you give CustomTag, and mount replaces them. It does not use Shadow DOM, so the page's CSS reaches its DOM. The sortable example drops a dragged row as a dimmed pending order until the committed order arrives, returns to the server's order when a save fails (the onError of the call changes a signal that is bound to an attribute), blocks new drags while an order is pending, waits for a drop before showing an update that arrives mid-drag, and applies a drop by key, not by screen position, after another tab reordered the list.

JSON attributes and Live View

A json attribute written in a Live View's render changes when a Topic redraws the Live View, and the change reaches update. The value is part of the page and update HTML, and the whole Live View is sent each time it redraws, so when a list has many rows, keep the update boundary small: split the list into smaller Live Views. There is no size limit on the attribute.

Loading the script

Serve the element's script from your own origin and load it with <script type="module" src=...>, as the rating example does. Build it with a bundler, as the examples do with bun build. The page's script-src 'self' policy applies to it as it does to the runtime.

What goes unchecked

  • An element registered with customElements.define instead of defineElement is not compared with its declaration. An attribute it does not read changes nothing, an event it never dispatches runs nothing, and a detail of another shape reaches the statements as it is (null when it is not JSON).
  • A json value is read with JSON.parse and not checked against T in the browser. A value that does not parse or nests more than 64 levels deep reads as missing.
  • The type does not check a key of bindElement that is not declared when the object comes from a variable.
  • A Live View update is sanitized before it is applied. A custom element keeps the attributes DOMPurify allows on any element, data-* and aria-*, and other attributes that pass the name rules above. Only DOMPurify's allowed attributes have their URL values checked, so an attribute outside that list keeps any value, such as a javascript: URL; the element's JavaScript must not use it as a link without checking it. Customized built-in elements (is) are not admitted.
  • Neither the server render nor the update sanitizer removes hypersig attributes, such as data-hs-on-click or data-hs-view, because they are data-* attributes. HTML that carries them runs Actions and signal expressions as the application's own markup does. Never pass user-supplied HTML through Hono's raw() or dangerouslySetInnerHTML; render it as text.

Redis Pub/Sub

hypersig-ts/redis delivers publications between processes through Redis Pub/Sub. Pass the result as pubsub to createHypersig or createLiveRuntime. See Deliver changes through Redis for the wiring of node-redis, ioredis, and Bun.RedisClient.

createRedisPubSub(options)
Returns a Pub/Sub with disconnected(). Within one adapter, the views that subscribe to the same Topic share one Redis subscription, which ends with the last of them.
publish(channel, message)
Required. Sends PUBLISH from a connection that is not in subscriber mode. The adapter's publish resolves when this resolves, which should be once Redis has accepted the command. The message is empty, since subscribers read the current value again.
subscribe(channel, onMessage)
Required. Subscribes on a connection in subscriber mode, calls onMessage for each message on the channel, and resolves once Redis has confirmed the subscription, with a function that ends it. A rejection reaches the runtime, which reports subscribe-error and tries again after a second. A channel can be subscribed again before ending the previous subscription has finished, so the returned function must end only the subscription it came from. TypeScript does not check this: a function that ends every listener on the channel stops the newer subscription, and its views stop updating.
channelPrefix
Optional. Defaults to "hypersig:". A Topic's channel is this prefix followed by the JSON of its name and key, such as hypersig:["counter","main"].
disconnected()
Call when the client reports that the subscriber connection dropped or came back. Every subscription made so far, including one still waiting for Redis, ends and calls its onDisconnect, so the live runtime subscribes again and reads its views again. A message published while the connection was down is not delivered later, and nothing checks that the application calls this; without it, the views on that process stay stale until the next change or reconcileIntervalMs.

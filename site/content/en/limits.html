Performance and limits

Serving HTML updates involves reading data, rendering HTML, and sending it to each connection. The cost depends on what each change updates and how many connections are displaying that data.

The cost of reading the same data for each connection

An update reloads the views subscribed to the change. The initial implementation loaded the view separately for each connection. If 200 connections displayed the same counter and each load ran one SQL query, a single change could trigger 200 identical reads.

An application can opt into sharing overlapping reads inside the server when they need the same data, access scope, and committed revision. The application specifies which reads and revisions can be shared.

In a local test with 200 connections to the same counter, the number of SQLite SELECT queries loading the view dropped from 200 to 1 per update, or from 2,400 to 12 over 12 updates. The test picked the revision from memory and added a 12-millisecond wait before each read. Time to deliver an update to every connection stayed about the same.

Permission checks and delivery still run per connection. If the application uses a SQL query to select the revision, that read still happens. Read sharing benchmark and reproduction steps

How much rendering and transfer can be avoided

The server renders the subscribed part of the page and sends its HTML to each connection. The browser applies only the necessary DOM changes within that part. When a count changes frequently, a fixed list can sit outside the area updated with the count.

In a published local benchmark with 500 rows in the initial HTML and 200 connections, moving the list out of the updated view reduced each update event from 23,924 B to 102 B. The unrelated view rendered zero times during those updates. The figures describe this specific page. Benchmark setup and reproduction steps

The server can also share the work of generating the same HTML from identical load results. This reduces rendering work. Each browser still receives its own update.

What happens when a connection drops

While disconnected, the page shows the last state it received. Reconnecting renders from the current data on the server. If a save commits and a failure interrupts publication, an open page may miss that change. To retry delivery, the application can record a pending notification in the same transaction as the save.

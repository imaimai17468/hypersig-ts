Performance and limits

Serving HTML updates involves reading data, rendering HTML, and sending it to each connection. The cost depends on what each change updates and how many connections are displaying that data.

Can an update increase SQL traffic

Yes. The application's load function reads the data. During a normal update, only views subscribed to the change load again. Pending notifications for the same view on one connection can be combined. Initial connection and reconnection also read data to synchronize the display.

If 200 connections subscribe to the same order count and every load runs a SQL query, one change can cause 200 reads. Rendering a smaller view can reduce work and transfer size. If the loader runs the same query, the number of reads stays the same.

How much rendering and transfer can be avoided

The server renders the subscribed part of the page and sends its HTML to each connection. The browser applies only the necessary DOM changes within that part. When a count changes frequently, a fixed list can sit outside the area updated with the count.

In a published local benchmark with 500 rows in the initial HTML and 200 connections, moving the list out of the updated view reduced each update event from 23,924 B to 102 B. The unrelated view rendered zero times during those updates. The figures describe this specific page. Benchmark setup and reproduction steps

Work that can be shared across connections

These measurements use an implementation in development. Render sharing reuses HTML when loads for the same view return equal values. Read sharing lets overlapping loads reuse one read when they need the same data, access scope, and committed revision.

In a local benchmark with 200 connections displaying the same counter and 12 sequential updates, sharing reduced HTML renders from 2,400 to 12. In a separate run, read sharing also reduced SQLite SELECTs from 2,400 to 12. That run selected the data revision from memory and waited 12 milliseconds before each SELECT. The time to deliver each update to all connections stayed similar.

Authorization checks and delivery still happen per connection. If selecting the data revision requires a SQL query, that read still happens. In your application, measure query count, rendering time, and transfer size separately.

What happens when a connection drops

While disconnected, the page shows the last state it received. Reconnecting renders from the current data on the server. If a save commits and a failure interrupts publication, an open page may miss that change. To retry delivery, the application can record a pending notification in the same transaction as the save.

Work that belongs in the browser

The browser can handle focus and unfinished input. Operations that need immediate computation on each gesture, such as drawing, and features that need to save offline require browser-side logic. hypersig.ts handles delivery and display of changes committed on the server.

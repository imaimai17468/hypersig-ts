Deployment

Run the application on a server that can render HTML, handle POST requests, and keep SSE connections open.

Serve the browser runtime

Run mise exec -- bun run build to produce dist/runtime.js. Serve the file from the application origin and include it using page.runtime("/runtime.js").

This site is static. Run the examples on your application server to try live updates.

Configure access

Set the public origin and provide a stable session identifier from authentication. Check access in each Action and Live View. Use the application database for persistent state.

Run multiple instances

The registration of each page is an encrypted token in the URL of the first HTML, and the server keeps no per-page registration, so multiple instances need no sticky routing. Give every instance the same pageKeys (base64 strings of 32 bytes). The first key encrypts and every key is tried to decrypt. When omitted, the keys are random per process, and a connection that arrives after a restart or at another instance gets reset and fetches the page again. Also give every instance the same session secret, or whatever signs or stores sessions, so a session made on one instance authenticates on the others.

A token expires 12 hours after the HTML was rendered (change it with pageLifetimeMs). A connected page keeps receiving updates past expiry: each time a stream ends at maxStreamMs, the server authenticates the user again and, while they can still read every top-level view on the page, sends a renewed token with a new lifetime, and the browser opens the next stream with it. A page that could not connect for pageLifetimeMs after its last token, such as one offline, asleep, or in the back/forward cache, or whose user could no longer read one of its views when its stream ended, fetches the page again on its next connection after that token expires. When instances are replaced one by one, rotate keys in two deploys. First add the new key after the current one on every instance; in this phase it only opens tokens. Then move the new key to the front, and remove the old key once pageLifetimeMs has passed since the last instance stopped sealing with it. Adding the new key in front in one deploy resets pages whose tokens an instance without the new key receives. Each token uses a random 96-bit nonce, so one key can safely encrypt about 2^32 tokens. Rotate well before a key reaches that count: at least once a year for a busy service.

For cross-instance changes, use a Pub/Sub adapter that delivers notifications to the instances serving those views.

Check that your proxy forwards SSE without buffering and allows long-lived connections.

Deploy a new version

A token stays valid across a deploy until it expires, so the new server opens tokens the old one rendered. The params in a token reach the new authorize, subscribe, load, and key as if they had the new params type. When you change the shape of a view's params, give the view a new name, so old tokens get reset, or remove the keys that sealed the old tokens from pageKeys.

A change to a template alone shows at the view's next update. A view the browser left untouched, whose snapshot revision has not moved, keeps the old HTML until its data changes. A page that stays open keeps its old browser runtime and talks to the new server, so keep the runtime compatible across a deploy, or remove the keys that sealed the old tokens.

Production checklist

  • Serve over HTTPS with HTTP/2 or later. Each open tab holds one SSE connection, and over HTTP/1.1 a browser opens only about 6 connections per origin, so a few tabs can stall other requests.
  • Set session cookies with Secure, HttpOnly, and SameSite=Lax or Strict. Use the __Host- prefix where the cookie needs no Domain and can use Path=/.
  • Send frame-ancestors in the Content-Security-Policy (or X-Frame-Options) with every page. With it and SameSite cookies, a cross-site page cannot open your pages in frames that use up maxStreamsPerSession and evict the user's tabs. A Lax cookie still goes with a popup another site opens, so use Strict to stop that as well.
  • Give every session its own sessionId. Sessions that share one, such as "anonymous" for every signed-out visitor, share one maxStreamsPerSession budget, so one visitor's tabs evict another's.
  • Render connectionStatusOutlet() on every live page. A tab past maxStreamsPerSession stops updating, and without the outlet only data-hs-connection changes, so the user is not told to reload.
  • Send a Content-Security-Policy with every page. Set it on the Response that hypersig.page() returns, with response.headers.set(...). Hono does not add headers set with c.header() to a Response the handler returns.
  • Give every instance the same session secret and the same pageKeys. Do not rely on the random key each process makes when pageKeys is omitted when you run more than one instance.
  • Use different pageKeys for each application and environment. pageContext binds tokens to the origin by default. When one application serves several origins, set the same pageContext explicitly on every instance.
  • Strip or hash /_hypersig/stream/* paths in access logs. The page token is in the path.
  • Rate-limit page renders and requests to /_hypersig/stream/*. maxStreamsPerSession counts streams in one process, not across instances.
  • Make authenticate consult revocable server-side state, such as a session store, and do not extend an idle expiry when a stream calls it. An open stream authenticates with the request it opened with, and reads the browser's current credentials only when it reconnects, at most maxStreamMs (30 minutes by default) later.

Troubleshoot saves and live updates

  1. In the browser developer tools, check the response to the POST. If the save fails, check input validation, authorization, and the configured public origin.
  2. If the save succeeds but the view stays stale, check the SSE connection in the network panel. If it stays open without an update event, check publication after the save, the view subscription, and access to the view.
  3. Open the same data in another tab and check that both tabs update. Take one tab offline briefly and check that it catches up after reconnecting.

Retrying notifications after a save

If the process stops after a save and before publication, open pages can miss the update. With SQLite, for example, you can record the data change and the pending notification in the same transaction. This pattern is called a transactional outbox.

After the save commits, the sender publishes the notification and removes it once the delivery service accepts it. Failed sends are retried. Use persistent storage to resume retries after a restart. This guarantee covers writes that also record the notification.

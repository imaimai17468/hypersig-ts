Deployment

Run the application on a server that can render HTML, handle POST requests, and keep SSE connections open.

Serve the browser runtime

Run mise exec -- bun run build to produce dist/runtime.js. Serve the file from the application origin and include it using page.runtime("/runtime.js").

This site is static. Run the examples on your application server to try live updates.

Configure access

Set the public origin and provide a stable session identifier from authentication. Check access in each Action and Live View. Use the application database for persistent state.

Run multiple instances

The registration of each page is an encrypted token in the URL of the first HTML, and the server keeps no per-page registration, so multiple instances need no sticky routing. Give every instance the same pageKeys (base64 strings of 32 bytes). The first key encrypts and every key is tried to decrypt. When omitted, the keys are random per process, and a connection that arrives after a restart or at another instance gets reset and fetches the page again. Also give every instance the same session secret, or whatever signs or stores sessions, so a session made on one instance authenticates on the others.

A token expires 12 hours after the HTML was rendered (change it with pageLifetimeMs). A connected page keeps receiving updates past expiry: each time a stream ends at maxStreamMs, the server authenticates the user again and, while they can still read every top-level view on the page, sends a renewed token with a new lifetime, and the browser opens the next stream with it. A page that could not connect for pageLifetimeMs after its last token, such as one offline, asleep, or in the back/forward cache, or whose user could no longer read one of its views when its stream ended, fetches the page again on its next connection after that token expires. When instances are replaced one by one, rotate keys in two deploys. First add the new key after the current one on every instance; in this phase it only opens tokens. Then move the new key to the front, and remove the old key once pageLifetimeMs has passed since the last instance stopped sealing with it. Adding the new key in front in one deploy resets pages whose tokens an instance without the new key receives. Each token uses a random 96-bit nonce, so one key can safely encrypt about 2^32 tokens. Renewals count too: besides the token each page render seals, every connected tab seals about one token per maxStreamMs. Rotate well before a key reaches that count: at least once a year for a busy service.

Deliver changes through Redis

A change published on one instance must reach the instances serving the views that subscribe to it. createMemoryPubSub() reaches only its own process. createRedisPubSub() from hypersig-ts/redis delivers each publication through Redis Pub/Sub to every instance connected to the same Redis, and the package depends on no Redis client: pass the publish and subscribe calls of the client you use. Use two connections, since a connection in subscriber mode cannot send other commands. Each Topic is the channel hypersig: followed by its name and key; set channelPrefix to keep apps that share one Redis apart. Pub/Sub channels ignore the database number chosen with SELECT, so apps or environments on different databases of one Redis still need different prefixes. Redis Cluster and Sentinel work as far as the client supports them. Workers cannot open TCP connections to Redis; use the Durable Object setup in Running with Void there.

With node-redis:

import { createClient } from "redis";
import { createRedisPubSub } from "hypersig-ts/redis";

const client = createClient({ url: process.env.REDIS_URL });
const subscriber = client.duplicate();
const pubsub = createRedisPubSub<AppEvent>({
  publish: (channel, message) => client.publish(channel, message),
  async subscribe(channel, onMessage) {
    const listener = () => onMessage();
    await subscriber.subscribe(channel, listener);
    return () => subscriber.unsubscribe(channel, listener);
  },
});
client.on("error", console.error);
// node-redis reconnects and queues the new subscriptions until it is back.
subscriber.on("error", () => pubsub.disconnected());
await Promise.all([client.connect(), subscriber.connect()]);

const hypersig = createHypersig({ origin, pageKeys, pubsub, authenticate });

With ioredis, which reports every message to one listener:

import Redis from "ioredis";
import { createRedisPubSub } from "hypersig-ts/redis";

const client = new Redis(process.env.REDIS_URL);
const subscriber = client.duplicate();
client.on("error", console.error);
subscriber.on("error", console.error);
const listeners = new Map<string, Set<() => void>>();
subscriber.on("message", (channel: string) => {
  for (const listener of listeners.get(channel) ?? []) listener();
});
const pubsub = createRedisPubSub<AppEvent>({
  publish: (channel, message) => client.publish(channel, message),
  async subscribe(channel, onMessage) {
    const channelListeners = listeners.get(channel) ?? new Set();
    const listener = () => onMessage();
    channelListeners.add(listener);
    listeners.set(channel, channelListeners);
    const end = async () => {
      channelListeners.delete(listener);
      if (channelListeners.size > 0) return;
      listeners.delete(channel);
      await subscriber.unsubscribe(channel);
    };
    try {
      await subscriber.subscribe(channel);
    } catch (error) {
      await end().catch(() => {});
      throw error;
    }
    return end;
  },
});
let isClosing = false;
// quit() and disconnect() emit close too, so shutting down skips it.
subscriber.on("close", () => {
  if (!isClosing) pubsub.disconnected();
});
async function closeRedis() {
  isClosing = true;
  await Promise.all([subscriber.quit(), client.quit()]);
}

With Bun.RedisClient:

import { RedisClient } from "bun";
import { createRedisPubSub } from "hypersig-ts/redis";

const client = new RedisClient(process.env.REDIS_URL);
await client.connect();
const subscriber = await client.duplicate();
const pubsub = createRedisPubSub<AppEvent>({
  publish: (channel, message) => client.publish(channel, message),
  async subscribe(channel, onMessage) {
    const listener = () => onMessage();
    await subscriber.subscribe(channel, listener);
    return () => subscriber.unsubscribe(channel, listener);
  },
});
// Bun 1.3.1 reconnects without subscribing again, so a reconnect means
// every subscription was lost. close() calls onclose too, so shutting down
// skips it.
let isClosing = false;
subscriber.onconnect = subscriber.onclose = () => {
  if (!isClosing) pubsub.disconnected();
};
function closeRedis() {
  isClosing = true;
  subscriber.close();
  client.close();
}

The Counter example uses the Bun.RedisClient wiring when REDIS_URL is set. The node-redis and Bun.RedisClient wiring are tested against a real Redis; the ioredis wiring was checked by hand against ioredis 5.11 under Bun and is not part of the tests.

node-redis and ioredis report every failed reconnect attempt, so disconnected() runs repeatedly during an outage; each call ends only the subscriptions made since the previous one, which is expected. The reconnect without subscribing again was seen on Bun 1.3.1; if a later Bun subscribes again by itself, the wiring above stays correct, since the runtime ends those subscriptions and makes new ones. On Bun 1.3.1 the reconnect delay also does not reset after a successful reconnect (it was seen growing from about 50 ms to a cap of about 2 s), so after later drops the views stay stale for up to about 2 seconds until onconnect; reconcileIntervalMs covers changes missed meanwhile.

Redis delivers each message once, to the instances subscribed when it receives the message, and keeps nothing for later. A message published while an instance's subscriber is disconnected never reaches that instance. When the client reports the drop, disconnected() ends every subscription, and the runtime subscribes again and reads every open view on that instance again, so the views show the changes made during the outage. Call it from the client's disconnect or reconnect event, as above; without it, those views stay stale until the next change or reload. publish resolves once Redis has accepted the message, not when other instances have rendered it.

Two losses remain: a process that stops after a save and before publishing, and a notification lost without the client noticing. For views that must catch up anyway, set reconcileIntervalMs, which re-reads the open views at that interval, or record the notification with the save and retry it, as in Retrying notifications after a save.

Check that your proxy forwards SSE without buffering and allows long-lived connections.

Deploy a new version

A token stays valid across a deploy until it expires, so the new server opens tokens the old one rendered. The params in a token reach the new authorize, subscribe, load, and key as if they had the new params type. When you change the shape of a view's params, give the view a new name, so old tokens get reset, or remove the keys that sealed the old tokens from pageKeys.

A change to a template alone shows at the view's next update. A view the browser left untouched, whose snapshot revision has not moved, keeps the old HTML until its data changes. A page that stays open keeps its old browser runtime and talks to the new server, so keep the runtime compatible across a deploy, or remove the keys that sealed the old tokens.

Production checklist

  • Serve over HTTPS with HTTP/2 or later. Each open tab holds one SSE connection, and over HTTP/1.1 a browser opens only about 6 connections per origin, so a few tabs can stall other requests.
  • Set session cookies with Secure, HttpOnly, and SameSite=Lax or Strict. Use the __Host- prefix where the cookie needs no Domain and can use Path=/.
  • Send frame-ancestors in the Content-Security-Policy (or X-Frame-Options) with every page. With it and SameSite cookies, a cross-site page cannot open your pages in frames that use up maxStreamsPerSession and evict the user's tabs. A Lax cookie still goes with a popup another site opens, so use Strict to stop that as well.
  • Give every session its own sessionId. Sessions that share one, such as "anonymous" for every signed-out visitor, share one maxStreamsPerSession budget, so one visitor's tabs evict another's.
  • Render connectionStatusOutlet() on every live page. A tab past maxStreamsPerSession stops updating, and without the outlet only data-hs-connection changes, so the user is not told to reload.
  • Send a Content-Security-Policy with every page. Set it on the Response that hypersig.page() returns, with response.headers.set(...). Hono does not add headers set with c.header() to a Response the handler returns.
  • Give every instance the same session secret and the same pageKeys. Do not rely on the random key each process makes when pageKeys is omitted when you run more than one instance.
  • Use different pageKeys for each application and environment. pageContext binds tokens to the origin by default. When one application serves several origins, set the same pageContext explicitly on every instance.
  • Strip or hash /_hypersig/stream/* paths in access logs. The page token is in the path.
  • Rate-limit page renders and requests to /_hypersig/stream/*. maxStreamsPerSession counts streams in one process, not across instances.
  • Make authenticate consult revocable server-side state, such as a session store, and do not extend an idle expiry when a stream calls it. An open stream authenticates with the request it opened with, and reads the browser's current credentials only when it reconnects, at most maxStreamMs (30 minutes by default) later.

Troubleshoot saves and live updates

  1. In the browser developer tools, check the response to the POST. If the save fails, check input validation, authorization, and the configured public origin.
  2. If the save succeeds but the view stays stale, check the SSE connection in the network panel. If it stays open without an update event, check publication after the save, the view subscription, and access to the view.
  3. Open the same data in another tab and check that both tabs update. Take one tab offline briefly and check that it catches up after reconnecting.

Retrying notifications after a save

If the process stops after a save and before publication, open pages can miss the update. With SQLite, for example, you can record the data change and the pending notification in the same transaction. This pattern is called a transactional outbox.

After the save commits, the sender publishes the notification and removes it once the delivery service accepts it. Failed sends are retried. Use persistent storage to resume retries after a restart. This guarantee covers writes that also record the notification.

Deployment

Run the application on a server that can render HTML, handle POST requests, and keep SSE connections open.

Serve the browser runtime

Run mise exec -- bun run build to produce dist/runtime.js. Serve the file from the application origin and include it using page.runtime("/runtime.js").

This site is static. Run the examples on your application server to try live updates.

Configure access

Set the public origin and provide a stable session identifier from authentication. Check access in each Action and Live View. Use the application database for persistent state.

Run multiple instances

The registration of each page is an encrypted token in the URL of the first HTML, and the server keeps no per-page registration, so multiple instances need no sticky routing. Give every instance the same pageKeys (base64 strings of 32 bytes). The first key encrypts and every key is tried to decrypt. When omitted, the keys are random per process, and a connection that arrives after a restart or at another instance gets reset and fetches the page again.

A token expires 12 hours after the HTML was rendered (change it with pageLifetimeMs). A connected page keeps receiving updates past expiry, and only a connection made after expiry fetches the page again. To rotate keys, add the new key first, keep the old key for the lifetime, then remove it.

For cross-instance changes, use a Pub/Sub adapter that delivers notifications to the instances serving those views.

Check that your proxy forwards SSE without buffering and allows long-lived connections.

Troubleshoot saves and live updates

  1. In the browser developer tools, check the response to the POST. If the save fails, check input validation, authorization, and the configured public origin.
  2. If the save succeeds but the view stays stale, check the SSE connection in the network panel. If it stays open without an update event, check publication after the save, the view subscription, and access to the view.
  3. Open the same data in another tab and check that both tabs update. Take one tab offline briefly and check that it catches up after reconnecting.

Retrying notifications after a save

If the process stops after a save and before publication, open pages can miss the update. With SQLite, for example, you can record the data change and the pending notification in the same transaction. This pattern is called a transactional outbox.

After the save commits, the sender publishes the notification and removes it once the delivery service accepts it. Failed sends are retried. Use persistent storage to resume retries after a restart. This guarantee covers writes that also record the notification.

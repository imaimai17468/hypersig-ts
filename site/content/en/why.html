Why hypersig

Server state can change while data is on its way to the browser. The design starts from the assumption that any page can go stale.

We look at how existing frameworks keep views up to date and which decisions are still left to the application. Then we explain what hypersig.ts takes on to reduce that work.

What remains in synchronization and typing

State synchronization and optimization in React

React is useful for updating views from browser state, such as in forms and editors. When the browser also holds server data, the application has to know which values become stale. Canceling an order can affect its detail view, the order list, and the order count.

Keeping those values in sync while limiting refetches and renders is hard. Narrowing an update takes experience. You need to decide which values to store or derive, then trace reads, writes, and renders to check that the views still agree. A developer or coding agent looking at one component cannot see where else the application uses the same data. React on redundant state and Effects

Updates after an action in Remix and rshono

Remix v2 reloads page data after a form submission and prevents older responses from overwriting newer ones. Remix 3 can update part of a page with HTML from another URL. In the rshono notes example, the save response includes fresh data for the page. Remix data revalidation · Response ordering · Remix 3 partial updates · Saving in rshono

When updates follow an action response, open pages still need a way to learn about later changes. For example, the page needs to learn that a scheduled job recalculated the order count before it can show the new value.

Partial updates and types in htmx

htmx applies server-rendered HTML to part of the page. The HTML attributes keep the request URL and update target near the element that triggers the request.

With the standard attributes, a type checker does not verify that the request or its target matches the application. You can generate htmx markup with JSX. If a URL or selector is written as a string attribute, TypeScript still cannot check its relationship to the server handler or the target element. htmx requests and update targets

Types and caching in TanStack Start

TanStack Start connects the types for URL search parameters and the data a route loads. The router can reuse cached loader results, and the application can also use TanStack Query.

When the application uses a cache, it decides which results can be reused and which to reload after a save. Updating the cached detail for a canceled order may leave cached lists and counts for various filters stale. The types can describe each result, while the application's order rules determine which results the cancellation affects. Route data loading and caching · TanStack Query invalidation after a write

The hypersig design

In hypersig.ts, a committed server change starts the update. You write views in typed JSX and use typed values for action input and for the changes each view subscribes to. The server determines which open views to update from those subscriptions.

The application announces a committed change, and the framework renders and sends the affected views. This keeps the browser's job to applying HTML and avoids updating a separate copy of the fetched data there. Server-rendered HTML with typed connections to server operations is an idea hypersig.ts takes from the Rust framework. The Rust hypersig design

Updating the page from a committed change

When a page opens in hypersig.ts, its server code declares which changes each view needs to receive. Suppose the application saves an order and then announces that change. The server renders the subscribed order list from the current data and sends its HTML. The browser applies that HTML to the corresponding region.

Another user looking at the same order receives the update according to their own page subscriptions. A scheduled job can announce the same change after saving it.

While saving or reconnecting

Application views display committed server data. A form can keep unfinished input and show that saving is in progress. The order list updates when HTML rendered from the saved data arrives.

Delivery takes time. After a connection drops, reconnecting reads the current state again. The application decides which changes to publish and how much of a page to update. A larger view can take more work to render on the server.

Why hypersig

The path from saving data to updating a page should be traceable in the server code. hypersig.ts defines that path from a committed change to the HTML applied to the affected parts of the page.

Keeping copies of server data in the browser

Consider a browser that fetches an order list and stores the count and total separately. After saving an order, the application has to refresh those values and handle the case where an earlier request comes back late. It also needs a way to learn about a change made by another user or a scheduled job.

Focus and unfinished input are local to the browser. A separate copy of shared application data must be kept current. What Remix changed about form submissions

Early Remix centered writes on HTML forms and HTTP. Remix v2 runs the server action and automatically reloads the data used by the page. Application code can leave revalidation to the framework. When requests overlap, Remix also decides which responses are current enough to apply. Remix v1 announcement · Data revalidation · Network concurrency

Updating one part of the page

Remix 3 can place HTML from another URL in a region called a Frame. A link, a form, or an explicit reload can select which region to update. Browser components also let the application explicitly decide when to render. Remix 3 Frames · Remix 3 design

rshono puts React components that read data on the server close to the server functions that update it. In its notes example, the response to a save includes fresh data for the page. The guide also shows how to display a tentative result while an action is pending. rshono forms and updates

These designs reduce the work involved in getting data from a server operation back to a page. Updating other pages that are already open also requires a way to identify who should receive the change.

Updating the page from a committed change

When a page opens in hypersig.ts, its server code declares which changes each view needs to receive. Suppose the application saves an order and then announces that change. The server renders the subscribed order list from the current data and sends its HTML. The browser applies that HTML to the corresponding region.

Another user looking at the same order receives the update according to their own page subscriptions. A scheduled job can announce the same change after saving it. The application code shows both where a notification is published and which views receive it.

While saving or reconnecting

Application views display committed server data. A form can keep unfinished input and show that saving is in progress. The order list updates when HTML rendered from the saved data arrives.

Delivery takes time. After a connection drops, reconnecting reads the current state again. The application is responsible for declaring the changes it publishes and the views that subscribe.

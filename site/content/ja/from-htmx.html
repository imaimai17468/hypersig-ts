htmx からの移行

htmx も hypersig.ts も、HTML をサーバーで生成します。違うのは、更新後の HTML がどこから届くかです。htmx ではリクエストへのレスポンスを対象の要素に差し込みます。hypersig.ts では Action がデータを変更して Topic を通知し、その Topic を購読するすべての Live View がサーバーで描画し直され、SSE で届きます。

考え方の違い

htmx の要素は URL、差し込み先のセレクター、差し込み方を指定し、サーバーはその 1 件のリクエストに、差し込む断片で応えます。ページのほかの部分やほかのタブは、レスポンスが指定したときだけ変わります。

hypersig.ts の Action のレスポンスが伝えるのは、成功か失敗かと Action の出力だけです。変更を確定した Action は Topic を通知します。各 Live View は自分が依存する Topic を宣言しているので、サーバーは開いているすべてのページで購読している表示だけを描画し、ブラウザはそれを morph で反映します。Action を送ったページにも、ほかのページと同じ経路で更新が届きます。

htmx のページが文字列として繰り返し書く名前（URL、項目名、差し込み先の ID、イベント名）は、hypersig.ts では値です。Action は hypersig.action() が返したオブジェクトから参照するので、Action 名の変更、フォームの項目名の打ち間違い、形の違う入力は、実行時に失敗するリクエストではなく型エラーになります。

対応表

hx-post、hx-get
Action です。ボタンには action.bind(input)、フォームには action.form()、Signal の文では action.call(input) を使います。Action は POST リクエストです。データの読み取りは、ページか Live View の描画で行います。
hx-target、hx-swap
page.view(view, props) で置く Live View の境界です。表示全体をサーバーで描画し、morph で反映するので、フォーカスや入力途中の値は残ります。beforeend のような差し込み方はないので、一覧全体を表示の中で描画します。
hx-swap-oob
同じ Topic を購読する複数の Live View です。1 回の通知ですべてが更新されます。
hx-vals、hx-include
bind() や call() に渡す型付きの入力か、action.field() で名前を付けたフォームの項目です。
hx-trigger
on.click、on.input、on.change、on.keydown、on.focusEnter、on.focusLeave です。delay: 修飾子は、イベントのたびに after() が数え直す timer() に置き換えます。every 2s のようなポーリングの代わりに、データが変わったときに Topic を通知します。
hx-indicator、htmx-request
送信中のフォームやボタンに付く data-hs-pending 属性か、action.pending() の Signal です。
hx-sync、hx-disabled-elt
リクエストが処理中のフォームやボタンは、もう一度送信されません。ほかの操作を止めるには bindAttr({ disabled: action.pending() }) を使います。
SSE 拡張
組み込みです。各ページは 1 本のストリームを開き、そのページのすべての表示の更新を受け取ります。切れると自動で再接続し、その際にサーバーの現在の状態を読み直します。
hx-boost、hx-push-url
通常のリンクです。リンクをたどると次のページをサーバーから読み込みます。クライアント側の画面遷移や履歴の操作はありません。リンクは Hono の型付きの $path() で作ります。
Alpine.js、_hyperscript
メニューの開閉や入力中の値など、ブラウザだけで決まる状態は Signal で書きます。JavaScript のライブラリや React の部品はカスタム要素の中で動かします。
エラーのレスポンス
項目ごとの検証メッセージには action.fieldError(name)、Action の失敗メッセージには errorOutlet() を使います。

ボタンで一部を更新する

htmx のサーバー側のルートは、新しい #counter の断片を返します。hypersig.ts では execute は数値を返し、HTML は counter から届きます。counter は counterChanged() を購読しているので、この表示があるすべてのページで描画し直されます。

入力に合わせた検索

Action は検索語をサーバーに保存し、セッションをキーにした Topic を通知します。そのため結果は、そのセッションのどのタブでも、最後に入力された検索語に合わせて変わります。searchDelay.after(300, ...) は、delay:300ms と同じく入力のたびに前の予約を取り消します。すでにページにある項目をリクエストなしで絞り込むなら、lit(name).includes(s.q) のような式を bindShow に渡します。

処理中の表示

data-hs-pending は、Live View の更新が先に届いても、その要素の最後のリクエストが終わるまで残ります。ページの値が変わるのは、リクエストを送ったときではなく、確定した更新が届いたときです。

Out-of-band の差し込み

Action は、ページのどこにメモが表示されているかを知る必要がありません。メモの一覧の表示と noteCount がどちらも notesChanged() を購読していれば、同じ Topic を通知するバックグラウンド処理からも更新されます。

フォームと検証エラー

<form {...addNote.form({ resetOnSuccess: true })}>
  <input name={addNote.field("text")} />
  <p {...addNote.fieldError("text")}></p>
  <button type="submit">Add</button>
  <p role="alert" {...errorOutlet()}></p>
</form>

addNote.field("text") は、名前を入力スキーマと照合します。送信された値はサーバーが検証し、ランタイムは項目のメッセージを fieldError で示した要素に、Action の失敗を errorOutlet() に書き込みます。JavaScript なしで送信されたフォームを受け付けるには、Action に formResponse を定義し、ページを返すかリダイレクトします。

Alpine.js の代わりにブラウザ側の状態を書く

Signal の式は型付きのメソッドで組み立て、データとして属性に入ります。初回の表示ではサーバーが束縛を評価するので、ランタイムが動き出す前からメニューは閉じた状態で描画されます。 ブラウザ側の Signal

Content Security Policy

htmx は hx-on のハンドラー、トリガーのフィルター、js: の値を eval で評価します。そのため 'unsafe-eval' を許可しないポリシーでは htmx.config.allowEval = false が必要になり、これらの機能は使えなくなります。Alpine.js の標準ビルドも 'unsafe-eval' を必要とします。

hypersig.ts のランタイムは、自分のオリジンから配信する 1 つのスクリプトです。Signal の式と文はランタイムが解釈する JSON なので、ページは 'unsafe-eval' もインラインスクリプトも使わずに script-src 'self' で動きます。Live View の HTML は、ページに入る前に DOMPurify で無害化されます。サンプルは default-src 'none'; script-src 'self'; connect-src 'self' を送っています。

異なる動作

  • ライブ更新には JavaScript と SSE の接続が必要です。どちらもない場合、ページはサーバーで描画した HTML を表示し、通常の送信で HTML を返すのは formResponse を定義した Action だけで、それ以外の Action は JSON を返します。
  • 更新は Live View 全体を置き換えます。一緒に変わるものごとに表示を分け、あまり変わらない大きな一覧は、頻繁に更新される表示の外に置きます。
  • 表示はサーバーの状態から読み込みます。検索語のように 1 件のリクエストの中にしかない値は、入力に合わせた検索の例のようにサーバーに保存します。
  • Live View と Action は、それぞれ authorize でアクセスを確かめます。authenticate が null を返すと hypersig.page() は 401 を返すので、匿名の訪問者にも、それぞれ別の id のセッションを与えます。

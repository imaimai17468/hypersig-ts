性能と制約

サーバーで HTML を作って配信するため、負荷はデータの読み取り、HTML の生成、接続ごとの転送に分かれます。どこに負荷がかかるかは、更新する範囲と、そのデータを見ている接続数で変わります。

更新のたびに SQL が増えるか

増える場合があります。データ取得はアプリの load が担当します。通常の更新では、変更を購読している表示だけを読み直します。同じ接続で、処理待ちの通知が同じ表示に複数届いた場合はまとめます。接続時の同期や再接続でもデータを読み直します。

たとえば、200の接続が同じ注文の件数を購読し、取得処理が毎回 SQL を1回実行するなら、1回の変更で読み取りが200回発生しえます。表示範囲を狭くすると HTML 生成と転送は減らせますが、取得処理が同じなら SQL の回数は変わりません。

再描画と転送はどこまで減るか

通知を購読した表示の範囲をサーバーで描画し、その HTML を各接続に送ります。ブラウザは受け取った範囲の中で必要な DOM を更新します。たとえば、件数だけが頻繁に変わる画面では、固定の一覧を更新範囲の外に置けます。

公開済みのローカル計測では、初期表示に500行を含め、200接続でカウンターを更新しました。一覧を更新範囲から外すと、更新イベント1件は 23,924 B から 102 B になり、カウンターと関係のない表示の再描画は0回でした。これはその画面での比較です。 計測条件と再現手順

接続間で共有できる処理

以下は開発中の実装を使った計測です。 HTML 生成の共有は、同じ表示で取得結果が等しい場合に、生成した HTML を再利用します。読み取りの共有は、同じデータを同じ権限の範囲で、同じ確定済みの版から同時に読む場合に、進行中の読み取りを再利用します。

200接続で同じカウンターを表示し、12回の更新を順に実行したローカル計測では、HTML の生成は 2,400回から12回 に減りました。別の計測では、読み取りの共有によって SQLite の SELECT も 2,400回から12回 に減りました。この計測では、読む版をメモリ上で選び、各 SELECT の前に12ミリ秒の待ちを入れました。全接続への配信時間は同程度でした。

認可の確認とブラウザへの送信は接続ごとに行います。読む版を調べるために SQL を使うアプリでは、その読み取りも発生します。実際のアプリでは、SQL の回数、HTML の生成時間、転送量を別々に測ります。

接続が切れた場合の表示

切断中の表示は最後に受け取った状態のままです。再接続すると、その時点のサーバーのデータから表示を作り直します。保存が確定したあと、通知の前に障害が起きると、接続を維持している画面には変更が届かない場合があります。通知の配送を再試行できるようにする場合は、保存と同じトランザクションで送信待ちの通知を記録する方法があります。

ブラウザ内で処理する方が適した操作

フォーカスや入力途中の値はブラウザで扱えます。描画ツールのように入力ごとに即座に計算が必要な操作や、オフラインでの保存を前提とする機能には、ブラウザ側の処理が必要です。hypersig.ts が扱うのは、サーバーが確定した変更の配信と表示の同期です。

性能と制約

サーバーで HTML を作って配信するため、負荷はデータの読み取り、HTML の生成、接続ごとの転送に分かれます。どこに負荷がかかるかは、更新する範囲と、そのデータを見ている接続数で変わります。

同じデータを接続ごとに読むコスト

更新時にデータを読み直すのは、変更通知を受け取るよう指定した表示です。初期の実装では、その表示を開いている接続ごとにデータを読みました。そのため、同じカウンターを200接続で開き、取得処理が毎回 SQL を1回実行する場合、1回の変更で同じ読み取りが200回発生しました。

アプリが読み取りの共有を有効にすると、同じデータを同じ閲覧権限の範囲で、同じ確定済みの版から読み取る処理が重なったときに、その読み取りをサーバー内部で共有します。どのデータと版を共有できるかはアプリが指定します。

この仕組みを使い、200接続で同じカウンターを表示して12回更新したローカル計測では、表示データを取得する SQLite の SELECT が、1更新あたり 200回から1回 に減りました。12更新の合計が2,400回から12回です。版の選択はメモリ上で行い、各読み取りの前に12ミリ秒の待ち時間を設定した条件です。全接続への配信が完了するまでの時間は同程度でした。

アクセス権の確認とブラウザへの送信は接続ごとに行います。読む版を調べるためにアプリが SQL を使う場合は、その読み取りも残ります。 読み取り共有の計測条件と再現手順

再描画と転送はどこまで減るか

通知を購読した表示の範囲をサーバーで描画し、その HTML を各接続に送ります。ブラウザは受け取った範囲の中で必要な DOM を更新します。たとえば、件数だけが頻繁に変わる画面では、固定の一覧を更新範囲の外に置けます。

公開済みのローカル計測では、初期表示に500行を含め、200接続でカウンターを更新しました。一覧を更新範囲から外すと、更新イベント1件は 23,924 B から 102 B になり、カウンターと関係のない表示の再描画は0回でした。これはその画面での比較です。 計測条件と再現手順

同じ取得結果から同じ HTML を作る処理も、サーバー内部で共有できます。これで減るのは HTML の生成処理です。各ブラウザへの送信は引き続き必要です。

接続が切れた場合の表示

切断中の表示は最後に受け取った状態のままです。再接続すると、その時点のサーバーのデータから表示を作り直します。保存が確定したあと、通知の前に障害が起きると、接続を維持している画面には変更が届かない場合があります。通知の配送を再試行できるようにする場合は、保存と同じトランザクションで送信待ちの通知を記録する方法があります。

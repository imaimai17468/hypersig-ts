設計の背景

ブラウザに届くデータは、サーバーが読み取った時点のものです。そのあとに保存が確定すれば、画面は古くなります。hypersig.ts は、サーバーで確定した変更を起点に画面を更新します。

画面が古くなる理由

注文一覧は、取得した直後でも、その間に注文が追加されていれば古くなっています。画面から注文を保存するときは、一覧や集計をいつ取り直すか、古い応答が遅れて届いたときにどう扱うかも決める必要があります。定期処理でデータが変わったときや、通信が切れたときにも同じ問題が起きます。

フォームの入力やフォーカスはブラウザで管理できます。共有する業務データもブラウザに保存すると、そのコピーが最新かどうかを画面ごとに管理する負担が生じます。React のドキュメントでも、すでにある値から計算できる値を別の状態に持つと同期の処理が増えることや、データ取得の応答順に注意が必要なことを説明しています。 React の状態と Effect の解説

Remix がフォーム送信から解消したこと

初期の Remix は、HTML のフォームと HTTP を基本に置きました。Remix v2 では、フォーム送信でサーバーの処理を実行したあと、画面に必要なデータを自動で取り直します。開発者は保存のたびにクライアントのキャッシュを書き換える手順を書かずに済みます。再取得が重なったときも、古い応答で新しい表示を上書きしないようにします。 Remix v1 の発表 · データの再取得 · 並行するリクエスト

データ取得と表示更新の設計

htmx では、操作に使う HTML 要素に、どこへリクエストを送り、返ってきた HTML を画面のどこに入れるかを書けます。サーバーが生成した表示をそのまま使えるので、ブラウザで同じデータから画面を組み立て直す処理が減ります。 htmx の基本

TanStack Start では、ページに必要なデータをいつ読み込むかをルートに書き、サーバーで実行する処理を関数として定義できます。URL の検索条件から画面に渡すデータまで型がつながります。 TanStack Start の設計

Remix 3 では、画面の一部に別の URL が返す HTML を表示できます。この領域を Frame と呼びます。リンクやフォーム、明示的な再取得で、どの領域を更新するか指定できます。ブラウザ側でコンポーネントを動かす場合も、再描画のタイミングをコードで指定します。 Remix 3 の Frame · Remix 3 の設計

rshono は、サーバー側でデータを読み取る React のコンポーネントと、画面から呼べるサーバー関数を近くに置きます。公式のメモの例では、保存したリクエストの応答で、そのページの新しい表示に必要なデータも返します。応答を待つ間に仮の表示を出す方法も用意されています。 rshono のフォームと更新

これらの設計は、データ取得やサーバーで生成した表示の反映を扱いやすくします。すでに開いている別の画面も更新するには、どの画面に変更を届けるかを決める仕組みが要ります。

確定した変更から画面を更新する

hypersig.ts では、画面を開いたときに、どのデータの変更を受け取るかをサーバー側で登録します。たとえば注文の保存が確定したら、アプリのコードが注文の変更を通知します。その通知を受け取るよう登録した一覧は、最新の注文データから HTML を生成します。ブラウザは、その HTML を画面の該当部分に反映します。

同じ注文を表示している別の利用者にも、その人が画面を開いたときの登録に従って更新を送ります。定期処理も、データを保存してから同じ変更を通知できます。どの処理が通知を出し、どの表示が受け取るかは、アプリのコードで確認できます。

通信中や切断中の表示

画面に反映する業務上の値は、サーバーで確定した結果です。たとえば保存中のフォームは入力値と送信中の表示を持てます。注文一覧に出す値は、保存後に生成された HTML が届いたときに更新します。

確定から画面に反映されるまでには通信時間があります。接続が戻ったらサーバーの最新状態を読み直します。アプリには、変更の通知と、通知を受け取る画面をコードで指定する責任があります。

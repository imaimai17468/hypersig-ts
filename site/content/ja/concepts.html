基本概念

アプリのデータはサーバーで管理します。ブラウザは受け取った HTML を表示し、フォーカスや入力途中の値を保持します。

データが変わってから画面が更新されるまで

  1. フォーム送信などで、サーバー上の処理を実行します。この処理を Action と呼びます。
  2. 処理が完了したら、変更されたデータを通知します。通知の対象を表す名前とキーの組み合わせが Topic です。
  3. その通知を受け取るよう登録した画面の一部を更新します。この部分を Live View と呼びます。
  4. サーバーで該当部分の HTML を生成し、ブラウザに送ります。サーバーから開いている接続に通知を送る方式を Server-Sent Events（SSE）といいます。

画面からの操作に加え、定期実行などのバックグラウンド処理でも、データの変更後に同じ Topic を使って通知できます。

一緒に更新する箇所の決め方

別々に変わる表示は、別の Live View に分けます。注文明細と合計金額のように同じ時点のデータを表示したい場合は、一つにまとめます。

Live View のキーはランタイムが定義ごとに付けます。同じ親の下に同じ定義を複数置くときだけ key で区別します。最初のページ表示に必要な HTML もサーバーで生成します。

ブラウザ側の操作を加える

サーバーで生成したページにも JavaScript を追加できます。たとえば、ドラッグ中の位置をプレビューしたり、編集中の文字数を表示したりできます。保存する値はサーバーに送り、確定した結果をほかの表示にも反映するときは、通常の変更通知を使います。

JavaScript のライブラリや React の部品は、宣言の値として一度だけ書いたカスタム要素に入れ、defineElement または reactElement で実装します。実装の型は宣言から決まり、props は宣言した属性、emit は宣言したイベントだけを受け付けます。このアイランドはサーバーで描きません。サーバーは要素と、代わりに見せる内容などとして渡した子だけを描き、残りはブラウザで要素の JavaScript が描きます。Shadow DOM も使いません。サーバーは JSON を含む属性を渡し、要素はイベントを型付きの値として返します。要素の JavaScript が子を描くときは ownsChildren を指定します。このときは id が必要で（ないと型エラーになります）、Live View の更新は、タグと id が一致するときだけ要素と子を残します。カスタム要素

コンボボックス、タブ、開閉パネルのような部品は、Signal の文だけで書けます。キーは on.keydown、フォーカスの出入りは on.focusEnter と on.focusLeave、計算した要素へのフォーカスは refs()、トーストやデバウンスは timer()、分岐は when で書きます。キーの名前とタイマーの時間は、型で検査できる範囲は型で、できない部分は実行時に検査します。Signal は、パネルが開いているかどうかのように、ブラウザだけで決まる状態に使います。サーバーのデータを Signal に写して書き換えるのはおすすめしません。データの持ち主が二つになるためです。ブラウザ側の Signal

利用者自身の操作を未確定のまま見せる

基本はおすすめしません。送信中にランタイムが出す処理中の表示で十分です。ドラッグ、頻繁な個人の切り替え、自分で書いた本文の送信のように、どうしても必要な場面でだけ使います。

ページはサーバーの結果を予測しません。新しい行の key、合計、在庫、ほかの人の編集と合わせた結果は、サーバーが確定してから表示します。利用者自身の操作は、確定する前に未確定のまま見せることができます（pending echo）。切り替えたばかりのお気に入り、手を離した位置、送ったばかりのチャットの本文などです。ドラッグのような直接操作、往復が 300 ms ほどを超えると壊れたように見える頻繁で影響の小さい個人の切り替え、自分で書いた本文の送信に使います。ほかの人が同時に編集しうる値、サーバーが決める値（key、価格、在庫、権限）、検証で拒否されうる入力、支払いのように取り消せない操作には使わず、処理中の表示だけにします。

pending echo は次の三つの規則に従います。

  1. 表示した値を処理中として示します。ランタイムが送信元のコントロールに付ける data-hs-pending 属性に見た目を付け、支援技術向けには action.pending() で文言を出します。
  2. 失敗したら、クリックする前の値ではなく、最新の確定した値に戻します。送信中に別のタブの確定が届くことがあるためです。
  3. Live View から届いた確定した値で置き換えます。

action.call(input, { pending }) を使うと、規則 2 と 3 はランタイムが守ります。pending には、呼び出しを実行したときに表示する値を書く set の文を並べます。ランタイムは、Live View から届いた各パスの最新の確定した値を覚え、確定した値が届けばいつでも表示を置き換え、送信が失敗したら最新の確定した値に戻します。値は Live View から描く必要があり、Action はその値を描き直す Topic を発行する必要があります。部品のサンプル のお気に入りボタンはこの形です。ブラウザ側の Signal

接続が切れたとき

サーバーは、認証されたセッションごとに表示対象を記録します。再接続時は最新のデータを読み直します。HTML の生成時と配信前に、表示する権限を確認します。

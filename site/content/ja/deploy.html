デプロイ

ページの HTML を生成し、フォームからのリクエストを処理できるサーバーで実行します。画面の更新には、サーバーからブラウザに通知を送る Server-Sent Events（SSE）を使います。

JavaScript の配信

mise exec -- bun run build で dist/runtime.js を生成します。このファイルは、フォームから値を送信し、受け取った HTML を画面に反映します。アプリと同じオリジンで配信し、page.runtime("/runtime.js") で読み込みます。

画面の更新を試すには、サンプルをローカルで起動してください。

アクセス権の設定

アプリの公開 URL のオリジンを設定し、認証処理からセッションの識別子を返します。サーバー上で処理を実行する前と、HTML を配信する前にアクセス権を確認します。保存が必要なデータは、アプリのデータベースに置きます。

複数のサーバーでの接続

どの画面に更新を送るかは、暗号化したトークンとして最初の HTML の接続先 URL に入っています。サーバーはページごとの登録を持たないので、複数のインスタンスで動かすときに接続先を固定する必要はありません。すべてのインスタンスに、同じ pageKeys（32 バイトの鍵を base64 にした文字列）を渡します。先頭の鍵で暗号化し、すべての鍵で復号を試します。省くと起動ごとの乱数になり、再起動後や別のインスタンスに届いた接続は reset でページを取得し直します。セッションを署名する秘密鍵やセッションの保存先も全インスタンスで共有し、あるインスタンスで作ったセッションがほかのインスタンスでも認証されるようにします。

トークンは HTML を生成してから 12 時間（pageLifetimeMs で変更できます）で期限が切れます。接続中の画面は期限後も更新を受け続けます。接続が maxStreamMs で終わるたびに、サーバーは利用者を認証し直し、ページのトップレベルの View をすべて今も読めるなら、期限を新しくしたトークンを送り、ブラウザは次の接続をそのトークンで開くためです。最後のトークンから pageLifetimeMs の間接続できなかったページ（オフライン、スリープ、bfcache にあるページなど）や、接続が終わる時点で View のどれかを読めなくなっていたページは、そのトークンの期限後に接続し直したときにページを取得し直します。インスタンスを順に入れ替えるときは、鍵の入れ替えを 2 回の配備に分けます。まず新しい鍵を現在の鍵の後ろに足して、すべてのインスタンスに配備します。この段階の新しい鍵は復号にだけ使われます。次に新しい鍵を先頭に移して配備し、最後のインスタンスが旧い鍵での暗号化をやめてから pageLifetimeMs が過ぎたら旧い鍵を外します。1 回の配備で新しい鍵を先頭に足すと、新しい鍵を持たないインスタンスに届いたトークンのページは reset になります。トークンごとに 96 ビットの乱数の nonce を使うので、1 つの鍵で安全に暗号化できるトークンは約 2^32 個までです。トークンを新しくした分も数に入ります。ページの描画ごとのトークンに加えて、接続中のタブはそれぞれ maxStreamMs ごとに約 1 個のトークンを暗号化します。その数に届くよりずっと前に、利用の多いサービスでは少なくとも年に 1 回、鍵を入れ替えます。

Redis で変更を届ける

あるインスタンスで発行した変更は、その変更を購読する View を配信しているインスタンスに届ける必要があります。createMemoryPubSub() が届けるのは自分のプロセスの中だけです。hypersig-ts/redis の createRedisPubSub() は、Redis の Pub/Sub を使って、同じ Redis につないだすべてのインスタンスに発行を届けます。このパッケージは Redis のクライアントに依存しないので、使うクライアントの publish と subscribe の呼び出しを渡します。購読中の接続はほかのコマンドを送れないため、接続を 2 本使います。Topic ごとのチャンネル名は、hypersig: に Topic の名前とキーを続けたものです。1 つの Redis を複数のアプリで共有するときは、channelPrefix で分けます。Redis Cluster と Sentinel は、クライアントが対応する範囲で動きます。Workers からは Redis に TCP で接続できないため、Void に組み込む場合の Durable Object の構成を使います。

node-redis の場合：

import { createClient } from "redis";
import { createRedisPubSub } from "hypersig-ts/redis";

const client = createClient({ url: process.env.REDIS_URL });
const subscriber = client.duplicate();
const pubsub = createRedisPubSub<AppEvent>({
  publish: (channel, message) => client.publish(channel, message),
  async subscribe(channel, onMessage) {
    const listener = () => onMessage();
    await subscriber.subscribe(channel, listener);
    return () => subscriber.unsubscribe(channel, listener);
  },
});
client.on("error", console.error);
// node-redis は自動で再接続し、新しい購読を再接続まで待たせます。
subscriber.on("error", () => pubsub.disconnected());
await Promise.all([client.connect(), subscriber.connect()]);

const hypersig = createHypersig({ origin, pageKeys, pubsub, authenticate });

すべてのメッセージを 1 つのリスナーで受け取る ioredis の場合：

import Redis from "ioredis";
import { createRedisPubSub } from "hypersig-ts/redis";

const client = new Redis(process.env.REDIS_URL);
const subscriber = client.duplicate();
const listeners = new Map<string, Set<() => void>>();
subscriber.on("message", (channel: string) => {
  for (const listener of listeners.get(channel) ?? []) listener();
});
const pubsub = createRedisPubSub<AppEvent>({
  publish: (channel, message) => client.publish(channel, message),
  async subscribe(channel, onMessage) {
    const channelListeners = listeners.get(channel) ?? new Set();
    const listener = () => onMessage();
    channelListeners.add(listener);
    listeners.set(channel, channelListeners);
    const end = async () => {
      channelListeners.delete(listener);
      if (channelListeners.size > 0) return;
      listeners.delete(channel);
      await subscriber.unsubscribe(channel);
    };
    try {
      await subscriber.subscribe(channel);
    } catch (error) {
      await end();
      throw error;
    }
    return end;
  },
});
subscriber.on("close", () => pubsub.disconnected());

Bun.RedisClient の場合：

import { RedisClient } from "bun";
import { createRedisPubSub } from "hypersig-ts/redis";

const client = new RedisClient(process.env.REDIS_URL);
await client.connect();
const subscriber = await client.duplicate();
const pubsub = createRedisPubSub<AppEvent>({
  publish: (channel, message) => client.publish(channel, message),
  async subscribe(channel, onMessage) {
    const listener = () => onMessage();
    await subscriber.subscribe(channel, listener);
    return () => subscriber.unsubscribe(channel, listener);
  },
});
// Bun は再接続しても購読し直しません。
subscriber.onconnect = () => pubsub.disconnected();
subscriber.onclose = () => pubsub.disconnected();

カウンターのサンプルは、REDIS_URL があると Bun.RedisClient でつなぎます。node-redis と Bun.RedisClient のつなぎ方は実際の Redis で試験しています。ioredis のつなぎ方は試験していません。

Redis はメッセージを受け取った時点で購読しているインスタンスに一度だけ届け、後のために残しません。あるインスタンスの購読の接続が切れている間に発行したメッセージは、そのインスタンスには届きません。クライアントが切断を知らせたときに disconnected() を呼ぶと、すべての購読が終わり、ランタイムが購読し直して、そのインスタンスで開いている View をすべて読み直すので、切断中の変更も画面に出ます。上の例のように、クライアントの切断か再接続のイベントから呼びます。呼ばないと、それらの View は次の変更か再読み込みまで古いままです。publish が終わるのは Redis がメッセージを受け付けた時点で、ほかのインスタンスが描画した時点ではありません。

それでも取りこぼす場合が 2 つ残ります。保存のあと通知を発行する前にプロセスが止まった場合と、クライアントが気づかないまま通知が失われた場合です。それでも追いつく必要がある View には、開いている View を一定間隔で読み直す reconcileIntervalMs を設定するか、保存した変更の通知を再試行するのように、通知を保存と一緒に記録して再試行します。

プロキシを使う場合は、SSE の応答が途中でまとめられずに転送され、長時間の接続が維持されることを確認します。

新しいバージョンのデプロイ

トークンはデプロイをまたいで期限まで有効なので、新しいサーバーは古いサーバーが作ったトークンを開きます。トークンの params は、新しい authorize、subscribe、load、key に新しい params の型として渡ります。View の params の形を変えるときは、View の name を変えて古いトークンを reset にするか、古いトークンを暗号化した鍵を pageKeys から外します。

テンプレートだけの変更は、その View の次の更新から表示に出ます。ブラウザが手を加えておらず、スナップショットの版も変わっていない View は、データが変わるまで古い HTML のまま残ります。開いたままのページは古いブラウザランタイムのまま新しいサーバーと通信するので、ランタイムをデプロイをまたいで互換に保つか、古いトークンを暗号化した鍵を外します。

本番環境のチェックリスト

  • HTTPS と HTTP/2 以降で配信します。開いているタブはそれぞれ SSE の接続を 1 本使い、HTTP/1.1 ではブラウザが 1 つのオリジンに開く接続は約 6 本までなので、数枚のタブでほかのリクエストが止まることがあります。
  • セッションの Cookie には Secure、HttpOnly、SameSite=Lax か Strict を付けます。Domain が不要で Path=/ にできる Cookie には __Host- 接頭辞を使います。
  • すべてのページの Content-Security-Policy に frame-ancestors（または X-Frame-Options）を付けます。これと SameSite の Cookie があれば、別サイトのページが利用者のページをフレームで開いて maxStreamsPerSession の枠を使い切り、利用者のタブを追い出すことはできません。Lax の Cookie は別サイトが開くポップアップには送られるので、それも防ぐには Strict にします。
  • セッションごとに一意の sessionId を使います。未ログインの訪問者すべてに "anonymous" を使うように sessionId を共有するセッションは maxStreamsPerSession の枠も共有し、ある訪問者のタブが別の訪問者のタブを追い出します。
  • 更新を受けるページには connectionStatusOutlet() を描画します。maxStreamsPerSession を超えたタブは更新を止めますが、表示先がなければ変わるのは data-hs-connection だけで、再読み込みが必要なことが利用者に伝わりません。
  • すべてのページに Content-Security-Policy を付けます。hypersig.page() が返す Response に response.headers.set(...) で設定します。Hono は、c.header() で設定したヘッダーを、ハンドラーが返した Response には加えません。
  • すべてのインスタンスに同じセッションの秘密鍵と同じ pageKeys を渡します。複数のインスタンスで動かすときは、pageKeys を省いたときにプロセスごとに作られる乱数の鍵に頼りません。
  • アプリと環境ごとに別の pageKeys を使います。pageContext は既定でトークンをオリジンに結び付けます。1 つのアプリを複数のオリジンで配信するときは、すべてのインスタンスに同じ pageContext を明示します。
  • アクセスログでは /_hypersig/stream/* のパスを取り除くかハッシュにします。パスにページのトークンが入っています。
  • ページの描画と /_hypersig/stream/* へのリクエストにレート制限をかけます。maxStreamsPerSession は 1 つのプロセスの中の接続だけを数え、インスタンスをまたいでは数えません。
  • authenticate は、セッションストアのような取り消せるサーバー側の状態を確認し、接続から呼ばれたときにアイドル期限を延ばさないようにします。開いている接続は開いたときのリクエストで認証し、ブラウザの現在の資格情報を読むのは接続し直したときだけです。接続し直すのは遅くとも maxStreamMs（既定 30 分）後です。

保存や画面更新が動かないとき

  1. ブラウザの開発者ツールで、操作を送った POST の結果を確認します。保存が失敗した場合は、入力の検証、認可、設定した公開オリジンを確認します。
  2. 保存できても画面が更新されない場合は、ブラウザのネットワーク欄で SSE 接続を確認します。接続が続いていても更新イベントが届かなければ、保存後の通知、表示側の購読、表示の認可を確認します。
  3. 別のタブでも同じデータを開き、更新が両方に届くか試します。片方を一時的にオフラインにしてから再接続し、その間の変更が反映されるかも確認します。

読み取りや配信にかかる負荷

保存した変更の通知を再試行する

保存後に通知を送る前にプロセスが落ちると、その変更を開いている画面に届けられない場合があります。たとえば SQLite では、データの変更と送信待ちの通知を同じトランザクションに記録できます。この方式を Outbox と呼びます。

保存が確定したあとで通知を送り、配信基盤が受理したら送信待ちの行を削除します。失敗した行は再試行します。再起動後も再試行するには、データと通知を永続ストレージに保存します。この保証は、通知を同時に記録する保存経路に限られます。
